# CLAUDE.md

Rules for any agent or person working in this repo. Keep this file current.

## Project

landing-factory turns a niche into an original, near-Awwwards-quality Astro landing page, ready to deploy. Roadmap: `docs/roadmap.md`. Current state, next steps and working agreements: `docs/status.md` (read it first in a new or compacted session). Product direction: `docs/product-plan.md`; channels (web app and chat, not built yet): `docs/channels.md`. The root is the starter demo and the template source; every generated landing lives in its own workspace under `sites/<slug>/` (see "Sites").

## Language

All documentation, comments, commit messages and pull request descriptions MUST be written in English.

## Stack

- Astro 7, static output (`output: 'static'`), Node 22 (`.nvmrc`)
- Tailwind CSS v4 via `@tailwindcss/vite`; tokens as CSS variables in `src/styles/tokens.css` (`@theme`)
- React islands (`@astrojs/react`), only where interaction is needed
- Motion: GSAP + ScrollTrigger and Lenis, vanilla TypeScript, driven by `data-*` attributes
- Three.js (`three`, vanilla, no R3F) only where a landing needs 3D: opt-in `<Scene3D />` scenes built from code, poster first, lazy-loaded (see "3D scenes")
- TypeScript strict, `astro check`, Prettier (with `prettier-plugin-astro`)
- Deployment: GitHub Actions to the site's target (`site.config.json`): Cloudflare Pages (`wrangler pages deploy`, the default), Vercel, a VPS or shared hosting through `scripts/deploy.mjs`; per-branch previews where the target has them, production from `main`

## Sites

Each landing is a complete static Astro site in `sites/<slug>/` (slug rule `^[a-z0-9]+(-[a-z0-9]+)*$`), registered as the npm workspace `site-<slug>` through `"workspaces": ["sites/*"]` in the root `package.json`. One `npm ci` at the root installs everything; one root `package-lock.json`. Details and conventions: `sites/README.md`.

- Create: `npm run new-site -- <slug> [--title ... --lang ... --message ...]` copies `astro.config.mjs`, `tsconfig.json`, `src/layouts/`, `src/components/motion/`, `src/components/three/`, `src/components/legal/`, `src/components/forms/`, `src/styles/`, `src/env.d.ts`, `public/_headers`, `public/robots.txt` and `public/favicon.svg` from the root, and writes `package.json` (same dependency ranges as the root), `site.config.json` (`target: "cloudflare"`, `pagesProject: <slug>`), `CREDITS.md`, `README.md`, the planning templates `PROPOSAL.md` and `RUN.md`, an empty `assets.json` (image manifest), an empty `src/scenes/`, a `noindex` placeholder `src/pages/index.astro` and a default `noindex` `src/pages/404.astro` (BaseLayout, heading, link home; English or the `--lang` text), so the report's 404 item passes from the first build; the `/new-landing` build restyles it in the landing's design, and `section-shots.mjs --include-404` captures it for review (QA keeps excluding `404.html`). `three` and `@types/three` join the shared dependencies. It never copies the starter's pages or sections (the 3D layer, the legal components and the lead forms components are copied into every new site and the `/new-landing` build prunes the ones the landing does not use, see "Code quality"), and refuses invalid slugs and existing folders (`--allow-existing-docs` accepts a folder holding only top-level `*.md` planning docs such as `PROPOSAL.md`, `brief.json` and, next to a brief, its `assets/` folder, and never overwrites them). Then run `npm install` once and commit the updated `package-lock.json`.
- Multi-locale (opt-in, owner decision 2026-10-25): `npm run new-site -- <slug> --langs en,es [--lang <default>]` (two or more lowercase tags; the default locale is `--lang`, else the first) builds on Astro's built-in i18n routing with static output. It writes the `i18n` block into the site's `astro.config.mjs` (`locales`, `defaultLocale`, `routing: { prefixDefaultLocale: false }`: the default locale at the root, the others under `/<locale>/`; the `security.csp` block stays), a placeholder home page at `src/pages/index.astro` and `src/pages/<locale>/index.astro` for each other locale (the folder names equal the locales exactly), `src/i18n/ui.ts` (typed UI dictionary, one object per locale, `t(locale)`; `en` and `es` strings built in, other languages start in English marked to translate), `src/i18n/urls.ts` and copies `src/components/i18n/`. `BaseLayout` takes `<html lang>` from `Astro.currentLocale`, emits `<link rel="alternate" hreflang>` for every locale plus `x-default` (absolute URLs when `site` is set, relative otherwise; none on `noindex` pages) and a self-referencing canonical, and loads the alternates from `src/i18n/urls.ts` only when it exists, so a single-language site never imports `astro:i18n`. `LanguageSwitcher.astro` renders real links (`hreflang`, `lang`, `aria-current`), works without JavaScript, and there is never a redirect by browser language (static output cannot read it). The single `404.astro` stays in the default language. A site without `--langs` is unchanged: no `i18n` block, no `src/i18n/`.
- Build and check one site: `npm run build -w site-<slug>`, `npm run check -w site-<slug>` (`npm run check:sites` for all).
- QA one site: `npm run qa -- --site <slug>` builds and serves `sites/<slug>`, checks its pages, runs impeccable on `sites/<slug>/src` and writes `qa/<slug>/<timestamp>/` (`qa/<slug>/latest`). A `sites/<slug>/qa.config.json` overrides the root `qa.config.json` for that site; never lower a threshold to get a pass.
- Sites copy the starter at creation and may diverge; nothing is shared at runtime. The root `src/styles/global.css` excludes `sites/` and `scripts/` from Tailwind's class scan so a site never changes the starter's CSS.
- Each site has its own deploy target and settings (`sites/<slug>/site.config.json`: `target` `cloudflare`, the default and then its own Pages project, `vercel`, `vps` or `shared`) and its own `CREDITS.md`. Do not edit another site's folder from a site change.

## Generating a landing

`scripts/new-landing.sh <slug> (--niche "..." | --brief <file>) [--refs a,b] [--auto] [--dry-run] [--resume] [--max-attempts N] [--model M]` runs `scripts/preflight.mjs`, `npm run new-site`, `npm install`, then `claude -p "/new-landing ..."` (skill: `.claude/skills/new-landing/SKILL.md`) and writes `sites/<slug>/.run.log`. With a customer brief (`--brief <file>`, or an existing `sites/<slug>/brief.json`) `--niche` is optional, the brief is validated first (exit 1, nothing created) and `--lang` defaults to its `language`; see "Customer brief". A brief whose `languages` has two or more tags (or `--langs a,b`) makes a multi-locale landing: the script passes `--langs` to `new-site` and to the skill, which writes the copy of every locale as natural text (not a word-for-word translation) with the same sections, shared components, strings from `src/i18n/ui.ts` or per-locale content files, the switcher in every header and the locales listed under Decisions. Phases: brief, synthesis (`PROPOSAL.md`, with a `Signals:` line and an "Archetype blend" chosen with `pick-archetypes`), checkpoint (stops unless `--auto`), design system (`design-system/<slug>/MASTER.md` with a `landing-meta` block, ui-ux-pro-max only), build (design-taste-frontend for art direction, palette and type fixed), QA loop (`npm run qa -- --site <slug>` until it passes or attempts run out), impeccable polish once, final check (writes `layout-signature.json` first), `RUN.md`. Outcome is the `Result:` line of `sites/<slug>/RUN.md`; the script exits non-zero on `failed`.

- Legal pages: when `legal.markets` in the brief is non-empty, the build runs `node scripts/legal.mjs --site <slug> --write`, adds the legal notice and privacy policy pages the market requires (components from `src/components/legal/`) and links them from every page footer; with no market it adds none and Decisions says "legal requirements unknown". See "Legal compliance".
- Images: only `node scripts/find-images.mjs` (Commons API through the proxy, throttled, CC0 / public domain / CC BY / CC BY-SA; with `--source commons,met` also The Met Open Access, public-domain objects, recorded with `source: "met"` and the museum's `creditLine`, `credit: true`; `new-landing.sh --sources commons,met` for historical or cultural niches). Each file is recorded in `sites/<slug>/assets.json`; `node scripts/credits.mjs --site <slug>` regenerates the photo table of `CREDITS.md` (between `<!-- credits:start -->` and `<!-- credits:end -->`) and `src/data/credits.json` for the footer. Do not hand-edit those. The vendored taste-skill `assets.mjs` ignores the proxy and is not used.
- AI images: the fifth source, only for illustrative art (the one person image allowed is the owner portrait of a personal brand, see "AI images") and only when the customer allows it or there is no brief; `node scripts/ai-images.mjs` (see "AI images"). The skill's source order is the customer's files, then Commons and The Met for real-world subjects, then AI.
- Final check: `node scripts/check-landing.mjs --site <slug> [--refs urls]` fails on an uncredited image, stale credits, a source photo referenced from more than two places, a MASTER.md palette color or font missing from `tokens.css`, a standard text token pair (ink/paper, primary-contrast/primary, ...) below 4.5:1, a site that matches another on primary color, display font and hero type, a layout too close to another site's (`layout-diversity`, thresholds under `diversity` in `qa.config.json`; needs `sites/<slug>/layout-signature.json`, written by `node scripts/layout-signature.mjs --site <slug> --write` after the build; no signature on a site with others to compare fails, and `check-landing` never starts a browser), a `[data-scene]` in the built pages without a poster recorded in `assets.json` (or more than 2 scenes), an AI image without provenance, consent or a visible disclosure (`ai-provenance`, see "AI images"), a multi-locale site (an `i18n` block in `astro.config.mjs`) that breaks the `i18n` rule (a locale without its home page, a wrong `<html lang>`, hreflang alternates missing, not reciprocal or without `x-default`, no or a broken language switcher, config, `src/i18n/ui.ts` and brief locales that disagree, or a page showing another locale's UI strings; relative hreflang URLs only warn, `i18n-absolute-urls`; `ai-provenance` then checks the disclosure on every locale's home page in its language and `brief-facts` the business name on each), or (with `--refs`) 8 words in a row copied from a reference read in memory. A warning (never a failure) is printed when the signature is outside the primary archetype's ranges. Exit 0 passed, 1 failed, 2 the run broke. CI does not run `check-landing`.
- `design-system/<slug>/MASTER.md` (skeleton: `design-system/_template.md`) ends with a fenced `landing-meta` block: `primary: #rrggbb`, `display-font`, optional `body-font`, `hero: full-bleed-photo|split|typographic|video|illustration|collage`, and the blend: `archetype: <primary>[+<secondary>]` or `custom`, `traits: a, b` (`ref:<sheet>/<trait>` allowed). See "Design archetypes".
- Auto mode runs with `--permission-mode acceptEdits`; the commands the skill needs are allowed in `.claude/settings.json`. Generation never commits, pushes or deploys.
- Usage: `claude -p` runs with `--output-format stream-json --verbose` through `scripts/lib/claude-stream.mjs`, which keeps the readable log (assistant text, `[tool] Name: detail` lines; lines it cannot parse pass through unchanged), writes the final `result` event's tokens and `total_cost_usd` to `sites/<slug>/.run-usage.json` (git-ignored; `{ "reported": false }` when there is none) and `new-landing.sh` appends a `Usage:` line (or "not reported") to the end of `RUN.md`, under Totals. The exit code is still claude's own.

### Visual directions

Before a full build the customer can pick a look. `scripts/new-landing.sh <slug> --directions [--count 2|3]` (default 3) runs the brief, the signals and 2 or 3 directions, then QA, and stops with `Result: directions`; nothing of the full build runs. Each direction is a `noindex` page at `/directions/<id>/` (`a`, `b`, `c`) with a hero and one section from the brief's real copy, built from a different primary archetype (`pick-archetypes --top 8`), with its own palette and fonts from ui-ux-pro-max (only). Tokens are scoped to the page (`[data-direction="<id>"]` redefines the `--color-*`, `--font-*` and radius variables in `src/styles/directions/<id>.css`), so one build serves all of them and the site's own branch preview gives the customer the URLs. The home page becomes a `noindex` index. Guide: `docs/preview.md`.

- Record: `sites/<slug>/directions.json` (schema `scripts/lib/directions-schema.mjs`; unknown keys fail) and `DIRECTIONS.md`. `node scripts/directions.mjs check --site <slug>` (2 or 3 directions, different primary archetypes, no shared trio of primary hue family, display font and hero type, pages built and `noindex`), `choose --site <slug> --direction <id> [--notes "..."]` (a person relays the customer's choice and comments; refuses an unknown id and a site whose direction pages were already removed) and `show`. Exit codes 0, 1, 2.
- `--resume` on a site with `directions.json` and no choice is refused (exit 1, naming `directions.mjs choose`). With a choice the proposal's "Archetype blend" and the design system start from the chosen direction, its notes are fixed inputs, and the direction pages, styles and components are removed before the build. A site without `directions.json` builds as before.

## Customer brief

A real customer's requirement lives in `sites/<slug>/brief.json`, one validated file (schema and validator: `scripts/lib/brief-schema.mjs`, tool: `scripts/brief.mjs`, no new dependency). It holds business and offer (products, prices), audience, goal and calls to action with real URLs, tone, page `language`, contact data, the customer's own assets (with owner and permission), brand constraints, references liked and disliked, legal constraints and the deploy target. Unknown keys fail. A value chosen for the customer is listed in `assumed` (`{ "field": "contact.hours", "reason": "..." }`) and an unknown value stays empty: assumed and empty fields are never presented as customer facts.

- `node scripts/brief.mjs init --site <slug> [--niche ...] [--lang <tag>] [--force]` writes a skeleton; `validate (--site <slug> | --file <path>) [--json]`, `missing` (required first, then recommended in interview order), `summary` and `import --file <path> --site <slug>` (copies the brief and its local assets into the site). Exit codes: 0 valid, 1 invalid or required missing, 2 bad usage. Asset paths are relative to `sites/<slug>/` (with `--file`, to the file's folder).
- Personal brand: `business.personalBrand` (boolean, the customer's statement that the business is a person) and `brand.ownerPortrait` (`allowed`, `not-allowed` or empty, like `brand.aiImages`: the owner's consent to an AI portrait of themselves, never listed in `assumed`, validation fails with "owner-portrait consent cannot be assumed"). `brief missing` lists `brand.ownerPortrait` only when `business.personalBrand` is true; `summary` shows both; older briefs stay valid. See "AI images" for what the consent allows.
- Languages: `languages` (optional array of lowercase language tags, for example `["en", "es"]`). When it is not empty it contains `language`, which stays the default locale, with no duplicates (validation names the entry); one tag or none is a single-language page, two or more a multi-locale landing (see "Sites"). `brief missing` lists it among the recommended fields until answered, `summary` shows `[en, es; default en]`, and `/brief-intake` asks "one language or more?" without assuming the answer. Older briefs stay valid.
- Legal fields: `legal.markets` (`EU` or ISO 3166-1 alpha-2 codes), `legal.holder` (`name`, `taxId`, `address`, `email`, `register`), `legal.privacyContact` and `legal.processing` (`analytics`: `none|cookieless|cookies`, `forms`, `embeds`). Holder identity (`legal.holder`, `legal.privacyContact`, or `legal` as a whole) can never be listed in `assumed`: validation fails. `brief missing` lists the holder fields, the privacy contact and the analytics answer once a market is named. All are optional, so older briefs stay valid.
- SEO fields: `seo` (optional object: `primaryKeyword`, `keywords` up to 10, `serviceArea` up to 10 cities or regions, strings up to 120 characters, and `schemaType` from the closed list `SCHEMA_TYPES` in `scripts/lib/brief-schema.mjs`; unknown keys and types fail). `brief missing` lists `seo.primaryKeyword` and, when the brief has an address or a city, `seo.serviceArea`; `summary` shows them; a keyword chosen for the customer may be listed in `assumed`; older briefs stay valid. See "SEO".
- Lead forms: `forms` (optional array of at most 3 `{ id, purpose, fields, provider, accessKey? }`; `purpose` `valuation|contact|callback|quote`, `fields` from `name, email, phone, address, postcode, propertyType, size, message, preferredTime`, `provider` `web3forms|whatsapp`, `accessKey` a UUID). Unknown keys, values and duplicates fail; a form requires `legal.markets` and `legal.processing.forms: true`; the access key can never be listed in `assumed` (validation fails, like the holder identity). `brief missing` asks for `forms[i].accessKey` of each web3forms form that has none; `summary` lists the forms; older briefs stay valid. See "Lead forms".
- `/brief-intake <slug>` (`.claude/skills/brief-intake/SKILL.md`) is the interactive interview: it asks in the language the user writes in (separate from the page `language`), only for what is missing, validates after each answer and never invents prices, reviews or results. It is not run by `claude -p`.
- `/new-landing` takes brand, offer, audience, tone, calls to action, contact data, references (liked sheets go to `pick-archetypes`, disliked ones are "avoid") and brand constraints from the brief, and lists every assumed or empty field under Decisions. Customer files are recorded in `assets.json` with `source: "customer"`, `owner`, `permission` and `credit` (a public credit only when `credit: true`); `credits.mjs` lists them under "Provided by the customer".
- `check-landing` `brief-facts` (only when `brief.json` exists, reads `dist/index.html`, no browser): fails when a non-assumed business name, primary call-to-action URL, contact email or phone, product name or price is missing from the page, or sits in an element that also says a word of `brief.sampleWords` in `qa.config.json`.

## Exporting a site

`npm run export -- --site <slug> --out <dir> [--no-brief] [--no-lockfile] [--record <https-url>] [--dry-run]` (`scripts/export.mjs`, modules in `scripts/export/`) writes a standalone repository for one site, so a landing can live and deploy from its own GitHub repository. The site sits at the root of `<dir>` and `npm run qa`, `npm run report` and `node scripts/deploy.mjs` run there without `--site` (root mode). Guide: `docs/export.md`.

- **What it writes.** The site's files, the factory scripts QA, the report and the deploy need (found by following relative imports from fixed entry points in `scripts/export.mjs`, never a hand-kept list; an import outside `scripts/` or a non-literal `import()` stops the export), its own `package.json` with every dependency pinned to the version the factory `package-lock.json` resolved (wrangler only when the site can deploy through it) and a `package-lock.json` from `npm install --package-lock-only` (`--no-lockfile` skips it offline), `qa.config.json`, `.nvmrc`, Prettier config, `.gitignore`, a one-site `.github/workflows/ci.yml` (template `scripts/export/templates/ci.yml`, same gate and deploy steps as the factory's `site-qa-deploy` job, no `--site`), a README (template `scripts/export/templates/README.md`) and the planning documents under `docs/factory/`. Output is formatted with the factory's Prettier.
- **Lint.** The export writes `eslint.config.mjs` (the root file, unchanged) and a one-project `knip.json`, adds the five lint packages to `devDependencies` (pinned from the lockfile), the scripts `lint`, `lint:code` (`eslint src`) and `lint:unused`, and a `Lint` step after the format check in its workflow. It refuses a site that holds an unused layer (exit 1, "prune it first", nothing written); the layer check itself is not exported.
- **Never copied.** `dist/`, `node_modules/`, `.astro/`, `qa/`, `.run.log`, `.run-usage.json`, `.env*`, `EXPORTED.json`. A match of the report's provider secret patterns in a file of the site stops the export (exit 1, nothing written, only the masked match is printed). `brief.json` travels unless `--no-brief` (the report's legal checks read it from the repository root).
- **Refusals.** Exit 2 and nothing written: invalid slug, missing site, `--out` inside the factory (checked through the real path) or not empty, a `--record` URL that is not `https://`. Exit 1: a failed check or step; the command removes what it wrote. `--dry-run` prints the files, the dependencies and the workflow and writes nothing. `--root` (tests only) works only when `NODE_TEST_CONTEXT` is set.
- **The record.** `--record <https-url>` writes `sites/<slug>/EXPORTED.json` (`repository`, `exportedAt`, `factoryCommit`, `target`, `noBrief`; a transfer adds `transferredTo` and `transferredAt`, see "Revising a landing"). A site with that file is never listed by `scripts/changed-sites.mjs`, so the factory's CI neither builds nor deploys it; the folder stays as the record, `check:sites` still checks it and `check-landing` still compares new landings with its `layout-signature.json`.
- **Not exported.** `credits.mjs` and `legal.mjs` (they need `sites/<slug>/`), `check-landing`, the generation pipeline, the MCP server and AI image generation. Later factory changes and revised copy are carried into the repository by `scripts/sync-export.mjs` (see "Revising a landing"), never by a hand copy. The command never creates the GitHub repository, pushes or touches DNS.
- **Shared code.** The proxy helper lives in `scripts/lib/proxy.mjs` (the `analyze-reference` skill file re-exports it), so no copied script imports from `.claude/`. In root mode `scripts/landing-report.mjs` reads `brief.json` at the repository root when it exists (the starter has none).

## Handing off a landing

Moving a finished landing to its owner's own repository, host and domain is one guided flow: `/landing-handoff <slug>` (`.claude/skills/landing-handoff/SKILL.md`, interactive, not run by `claude -p`). Guide: `docs/handoff.md`.

- `node scripts/handoff.mjs check --site <slug> [--visibility public|private] [--json]` (`npm run handoff -- check ...`) is the read-only preflight: it exits 1 naming every problem (site missing or already exported, unused layer, invalid `site.config.json`, no `site` in `astro.config.mjs`, brief `deploy.domain` not the host of `site`, configured target different from the brief's) and warns when a public repository would carry `brief.json`. `plan --site <slug> --repo <owner>/<name> --visibility public|private [--old-host <name>]` prints the owner's Markdown checklist (empty repository, Claude GitHub App access, the secrets by name from `docs/deploy/<target>.md`, first run by hand, domain steps with the apex or `www` choice taken from `site`, where the DNS really lives, cleanup). Exit 0 ready, 1 not ready, 2 bad usage; secret values are never read.
- The exported workflow runs the live report on the landing's `site` domain on the production branch (`steps.target.outputs.is_production`), after the deployment report: `not-run` items and a green job while the domain does not answer, a failing item fails the job once it does.
- `node scripts/handoff.mjs transfer-plan --site <slug> --to <github-owner>` is the read-only checklist for transferring an exported landing's repository to its customer (the owner transfers it on GitHub, the customer's host project and secrets by name, the first run, the domain, the owner's cleanup); it exits 1 for a site never exported or already transferred. See "Revising a landing".
- The skill never asks for a secret in chat, never creates a repository or starts a workflow run (the Claude GitHub App answers 403 to both; the owner does them) and never changes DNS. It also covers the sync of an already exported repository with `sync-export.mjs` and the transfer to the customer.

## Revising a landing

Delivery model (owner decision, 2026-10-27): **managed, with transfer**. The owner builds in the factory, exports to a repository in his own account, hosts on his own Vercel or Cloudflare account, and transfers the repository to the customer if they want the project. While a landing is managed the factory is the source of truth: every change goes through `sites/<slug>/` and then a sync; a change made directly in the repository is overwritten by the next sync. Guide: `docs/revise.md`.

- **Revision round.** `scripts/revise-landing.sh <slug> --feedback <file> [--model M] [--max-attempts N]` (`npm run revise`) refuses (exit 1) a missing site, a transferred site, a site with direction pages and no build and a site without a finished build (`RUN.md` `Result: passed`); an empty, over-4000-character or missing feedback file is exit 2. It runs `claude -p "/revise-landing <slug> --round N --feedback-file <file> ..."` (skill: `.claude/skills/revise-landing/SKILL.md`, our own) through `scripts/lib/claude-stream.mjs`, logs to `sites/<slug>/.revise.log` and reads the `Result:` line of `sites/<slug>/REVISION.md` (`passed`, `failed`, `needs-rebuild`; overwritten each round). The skill classifies each feedback item (`fact`, `copy`, `content`, `style`, `rebuild`), updates `brief.json` first for facts, edits only `sites/<slug>/` and `design-system/<slug>/MASTER.md` with the build's rules, runs QA, the static report, `layout-signature --write`, `check-landing`, the layer check and lint, and never commits, pushes, deploys or syncs. A `rebuild` item stops the round before editing with `Result: needs-rebuild` (exit 0): a person decides between `--directions` and a new build.
- **Record.** `sites/<slug>/revisions.json` (schema `scripts/lib/revisions-schema.mjs`, unknown keys fail; helper `scripts/revisions.mjs`): per round the number, date, the feedback as the customer gave it, the items with their kind, `briefChanged`, the files, the result and the usage (added by the script from `.run-usage.json`, `null` when not reported). Rounds per landing and cost per round are read from it.
- **Sync.** `node scripts/sync-export.mjs --site <slug> --into <clone> [--brief|--no-brief] [--no-lockfile] [--dry-run]` re-exports into a scratch folder and mirrors it into the clone (add, change, delete), keeping `.git` and ignored paths, `package-lock.json` unless `package.json` changed (then regenerated) and `README.md` when only its export line differs, and prints the files and the count. It never commits or pushes. It refuses (exit 1, nothing written) a site without `EXPORTED.json`, a transferred site, a clone whose `origin` is not the recorded repository (`https`, `ssh` and `.git` forms compare equal, credentials ignored), a path that is not a work tree root and a clone with uncommitted changes. `noBrief` comes from the record; an older record without it needs `--brief` or `--no-brief` (exit 2). A person (or `/landing-handoff`) then runs `npm ci && npm run lint && npm run build` in the clone, pushes a branch and opens a pull request there; that repository's CI gives the customer's preview.
- **Transfer.** `node scripts/handoff.mjs transfer-plan` is the checklist; after the owner transferred the repository, `node scripts/transfer.mjs record --site <slug> --to <github-owner> [--repository <https-url>]` writes `transferredTo`, `transferredAt` and the new repository URL into `EXPORTED.json` (`scripts/lib/export-record.mjs` holds `isTransferred`, used by every refusal). From then on `revise-landing.sh`, `sync-export.mjs` and the MCP `revise_landing` job refuse the site, and the factory does nothing more with it; the folder stays as the record. Revisions inside a transferred repository, a factory GitHub organization, automatic sync and billing are out of scope.
- **Agent interface.** `revise_landing` (`slug`, `feedback` of at most 4000 characters, `model?`, `maxAttempts?`) is a `generation`-class job that writes the feedback to `.cache/jobs/<id>/feedback.txt` and runs `revise-landing.sh <slug> --feedback <that file>`; a transferred site is a tool error and no job starts. `get_landing` adds `revisions` (count and last round), `exported` and `transferred`. Sync and transfer are not tools: the interface never publishes. `revise-landing.sh`, `sync-export.mjs` and `transfer.mjs record` write, so a person approves each run; `.claude/settings.json` has no entry for them or for `revise_landing`.

## Agent interface

`scripts/mcp/server.mjs` is a local MCP server over stdio (hand-written JSON-RPC 2.0, newline-delimited, no SDK dependency; modules `protocol`, `tools`, `commands`, `jobs`, `run-job`, `landings`, `paths`, `redact`). It lets an agent drive the factory with every action except publishing. Guide: `docs/agent-interface.md`.

- **Tools.** `list_landings`, `get_landing`, `get_qa`, `get_report`; `brief_init` (never overwrites), `brief_validate`, `brief_missing`, `brief_summary`, `brief_update` (deep merge, arrays replaced, saved only if the result validates, never assumes `legal`, `legal.holder`, `legal.privacyContact` or `brand.aiImages`); `choose_direction` (writes only `directions.json`); jobs `propose_landing`, `preview_landing`, `generate_landing`, `revise_landing`, `run_qa`, `run_report`; `get_job`, `list_jobs`, `tail_job_log`, `cancel_job`. Tool failures are results with `isError: true`; an unknown tool is a JSON-RPC error (-32602). Protocol versions `2025-11-25`, `2025-06-18`, `2025-03-26`, `2024-11-05`: the client's is echoed if supported, else the newest. Only protocol JSON goes to stdout; logs go to stderr.
- **Jobs.** Each job is a detached process group started through `scripts/mcp/run-job.mjs`, with its state in `.cache/jobs/<id>/` (`job.json` by the server, `exit.json` by the wrapper, `log.txt`). They survive a restart of the server; states are `running`, `passed`, `failed`, `cancelled`, `lost`. One generation per landing; `MCP_MAX_JOBS` (`N` or `generation=1,check=2`) limits concurrency. Cancel is SIGTERM to the group, SIGKILL after 10 s. Jobs older than 30 days are pruned at start. Each records `durationMs`; generations also copy `sites/<slug>/.run-usage.json`.
- **Safety.** Every job runs one command of the fixed table in `scripts/mcp/commands.mjs` (`new-landing.sh`, `revise-landing.sh`, `qa.mjs`, `landing-report.mjs`) with validated arguments (slug rule, existing pattern sheets, model `^[a-z0-9.-]+$`, `https://` report URL; free text is one argv element, never a shell). The table must never contain deploy, wrangler, git, gh or push, and no tool publishes, commits, pushes, opens a pull request or edits `.claude/`, `CLAUDE.md`, the workflow or secrets (a test asserts it). Paths are built with `inside()` from validated parts; tools write only `sites/<slug>/brief.json`, `sites/<slug>/directions.json` and `.cache/jobs/`. Results and log tails pass through `scripts/mcp/redact.mjs` (the report's secret patterns, values of sensitive environment variables, `key = value`); there is no tool that reads the environment.
- **Tests.** `LANDING_FACTORY_ROOT` moves the repository root the tools read. `MCP_TEST_JOB_STUB` (a node script run instead of every job command) and `MCP_TEST_CANCEL_GRACE_MS` are honored only when `NODE_TEST_CONTEXT` is set, as the Node test runner does; no tool argument or production setting can pick a command. Tests: `tests/mcp-protocol.test.mjs`, `tests/mcp-tools.test.mjs`, `tests/mcp-jobs.test.mjs`; they never call `claude` or the network.
- **Permissions.** `.claude/settings.json` allows the read, brief and job-status tools (`mcp__landing-factory__<tool>`, listed one by one, no wildcard) and not `propose_landing`, `preview_landing`, `generate_landing`, `revise_landing`, `run_qa`, `run_report` or `cancel_job`: a person approves long jobs. When you add a tool, decide its permission there.
- **Out of scope:** HTTP transport, authentication, several users, containers per job, publishing or opening pull requests from the interface, MCP resources and prompts.

## Landing report

`npm run report -- [--site <slug>] [--url <deployed-url> | --site-url] [--external-links] [--only static|live] [--skip <groups>] [--qa <report.json>]` (`scripts/landing-report.mjs`, modules in `scripts/report/`) audits one landing for security, framed by the **OWASP Top 10:2025**, for performance and, in the `legal` area, for cookies, trackers, legal pages and price claims (see "Legal compliance"). It writes `report.json` and `report.md` to `qa/<slug>/report/<timestamp>/` (`qa/report/<timestamp>/` for the starter) and a `latest` link. Exit codes: 0 no item failed, 1 at least one item failed, 2 the run broke (bad usage or config, build error). Options: `npm run report -- --help`.

- Every item has an area (security, performance or legal), an OWASP category, a status (`pass`, `warn`, `fail`, `na`, `not-run`), the evidence (file, line, URL, measured value) and a fix. The verdict is `failed` only when an item fails; warnings, not-applicable categories and `not-run` items are always listed. A check that needs the network (npm audit, live checks, outbound links) and cannot reach it is `not-run`, never `pass`. The Markdown starts with the verdict and the counts; A06, A07 and A09 are reported as not applicable with the reason unless something applies.
- Static checks (no `--url`; build is made if `dist/` is missing): security headers in `dist/_headers` (nosniff, Referrer-Policy and `frame-ancestors` fail; HSTS, COOP, Permissions-Policy and a script CSP warn), the effective CSP per page (header plus `<meta http-equiv>`), private files in `dist/` (`.env`, `.git`, keys, `brief.json` fail; source maps and manifests warn), mixed content (fail) and `http://` links (warn), `javascript:` URLs, external scripts without SRI (fail) and stylesheets (warn), third-party origins, broken internal links and assets (fail), `target="_blank"` without `noopener`, the 404 page, forms and password fields, inline scripts against the CSP hashes, raw HTML sinks in `src/` (`set:html`, `innerHTML`, ...), secrets in the site folder and its build, `npm audit --omit=dev` for the workspace (high or critical fail unless listed with a reason in `report.audit.ignore`), and the lockfile.
- Secrets: provider patterns (private keys, AWS, GitHub, Slack, Stripe live, Google, OpenAI/Anthropic, npm) fail; the generic `token|password|api_key = '...'` pattern only warns; `.env` files (except `.example`, `.sample`, `.template`) in a site folder fail. Every match goes through `mask()` (`scripts/report/mask.mjs`: four characters and the length); never print or store a raw match, and never put a real-looking token in a fixture: tests build fake secrets at runtime.
- Legal area (`--skip legal` removes it): five items with stable ids, `legal-cookies`, `legal-third-party`, `legal-pages`, `legal-price-claims` and `legal-forms`, read from `dist/` and, behind the same freshness guard as the Lighthouse detail, from QA's `pages[].privacy` record. The Markdown ends the Legal section with the not-legal-advice line. Details and rules: "Legal compliance".
- SEO area (`--skip seo` removes it): nine items with stable ids, `seo-title`, `seo-description`, `seo-h1`, `seo-canonical`, `seo-open-graph`, `seo-structured-data`, `seo-sitemap`, `seo-robots` and `seo-keyword`, read from `dist/` over the indexable pages only (no `noindex`, `404.html` or `/directions/`; none left makes every item `na`). It fails only on a missing title or description, JSON-LD that does not parse, review or rating markup (the brief has no reviews), a `noindex` page in the sitemap or `Disallow: /` with indexable pages; every other gap warns. Limits: `report.seo` in `qa.config.json`. The inline-script inventory skips `application/ld+json`. Details: "SEO".
- `--site-url` (not with `--url`) takes the live URL from the build: the origin of the absolute canonical URL in `dist/index.html` (`scripts/report/site-url.mjs`; exit 2 when there is none, so `site` must be set in `astro.config.mjs`). Exported repositories use it for the production domain.
- Live checks (`--url https://...`, `--only live` for just these): valid TLS, HTTP redirects to HTTPS (a closed port or an unreachable plain HTTP is a warn or `not-run`, 200 fails), response headers and HSTS, long `immutable` caching of an `/_astro/` asset, private paths (`/.git/HEAD`, `/.env`, `/brief.json`, `/package.json`, `/assets.json`) judged by their body so a host that answers the home page for every path passes, and an unknown path that must answer 404. `--allow-http` (local servers) turns the TLS checks into n/a. `--external-links` requests each outbound link once (at most 50, sequential, 250 ms apart): 401, 403, 429, challenge headers and cancelled connections are listed as unverified, 404/410/5xx/DNS errors warn, and nothing is retried to get around a block (Etsy answers a bot challenge: it stays unverified).
- Performance: the report reads the Lighthouse detail QA stores in `qa/[<slug>/]latest/report.json` (`presets[].detail`: LCP element and time, CLS, TBT, weight, requests, image and font findings, render-blocking, third parties) and uses it only when that QA run finished after `dist/index.html` was built; otherwise those items are `not-run` ("run QA first"). A Lighthouse score under the QA threshold fails; the other measures (LCP, CLS, TBT, page weight, images over `maxImageKb`, JPEG or PNG over `legacyImageKb`, font faces, third-party origins) warn against `report` in `qa.config.json` (defaults in `scripts/report/config.mjs`; never raise a limit to hide a real problem).
- The starter ships a Content-Security-Policy from Astro's `security.csp` (hashes for the scripts Astro emits, `'unsafe-inline'` only in `style-src-attr`), HSTS and COOP in `public/_headers`, and `new-site` copies them. A policy in a `<meta>` tag only applies to what follows it, so an authored inline script before the tag (Motion's `is:inline`) is listed as outside the policy, not as an injection point. Never use `'unsafe-inline'` in `script-src`; if a script is blocked, add its origin to `scriptDirective.resources`. `tests/csp.test.mjs` loads the built starter in Chromium and fails on any `securitypolicyviolation`. Existing sites keep their copies and the report warns until each one opts in (HSTS, COOP, CSP) in its own site change.
- CI runs `npm run report -- --only static` after QA (root `qa` job and each site job; a failing report blocks the deploy) and `--only live --url <deployed URL>` after the deploy, uploads `landing-report` / `landing-report-live` / `landing-report-<slug>` and adds a `Report:` line to the sticky comment. See "CI and deployment".

## CI and deployment

`.github/workflows/ci.yml` (triggers: `pull_request`, push to `main`, `workflow_dispatch`) has two jobs. `qa` runs Prettier, `npm run lint`, `astro check`, `npm run validate:patterns`, `npm run validate:archetypes`, Chromium install, `npm test`, `npm run qa` and `npm run report -- --only static`, uploads the `qa-report` and `landing-report` artifacts, and, only if everything passed, the `site-dist` artifact (`dist/`). `deploy` has `needs: qa`, downloads `site-dist` and, for the default `cloudflare` target, runs `npx wrangler pages deploy dist --project-name <site.config.json> --branch <head_ref || ref_name>` (other targets: see "Deploy targets" below): `main` is the Pages production branch, every other branch gets a preview at `https://<branch-alias>.<project>.pages.dev`. After the URL capture `deploy` runs `npm run report -- --only live --url <deployment URL>` (`continue-on-error`, so the comment and the `landing-report-live` artifact are written first, then a last step fails the job if the live report failed). On PRs it posts one sticky comment (hidden marker `<!-- landing-factory-preview -->`) with the URLs and a `Report:` line (static and live verdicts and counts). The project is created idempotently if missing. URLs are read from wrangler's `WRANGLER_OUTPUT_FILE_PATH` ND-JSON via `scripts/parse-wrangler-output.mjs`.

Sites: the `sites` job runs `scripts/changed-sites.mjs` (full history, `fetch-depth: 0`) to list the sites whose `sites/<slug>/` changed, or all of them when a shared path changed (`package.json`, `package-lock.json`, `qa.config.json`, `src/components/motion/`, `src/layouts/`, `src/styles/`, `scripts/qa.mjs`, `scripts/qa/`, `scripts/landing-report.mjs`, `scripts/report/`, `scripts/lib/`, `scripts/parse-wrangler-output.mjs`, `scripts/deploy.mjs`, `scripts/deploy/`, `.github/workflows/`); manual runs build all. A site with `sites/<slug>/EXPORTED.json` (exported to its own repository, see "Exporting a site") is never listed, even when its folder or a shared path changed. The `site-qa-deploy` matrix job (one per site, skipped when the list is empty) runs `astro check`, `npm run qa -- --site <slug> --runs 3` (median of 3 Lighthouse runs, since one slow runner pass scored a site 67 that measures 97 to 99 locally), runs `npm run report -- --site <slug> --only static` right after QA, uploads the `qa-report-<slug>` artifact and, only if everything passed, deploys `sites/<slug>/dist` to the target in `sites/<slug>/site.config.json` (a Pages project for `cloudflare`) with the same secrets gate, project creation and URL capture as `deploy`, then runs the live report on the deployment URL and uploads `landing-report-<slug>` (both runs). On PRs each site gets its own sticky comment (marker `<!-- landing-factory-preview:<slug> -->`) with its `Report:` line. The root `qa` job also runs `npm run check:sites`.

Deploy gating: after `Read deploy target`, the `Check deploy prerequisites` step checks that the secrets the effective target needs are set (never echoing them: it only sees booleans like `secrets.X != ''`) and that the PR is not from a fork (the site jobs apply the same gate after their QA passes). If not, it emits a `::warning::` naming what is missing and skips the remaining deploy steps (job stays green). Never print, log or commit credentials; never deploy from a local machine. Docs for setup: README, "Deployment", and `docs/deploy/`.

Deploy targets: `site.config.json` has `target` (`cloudflare` by default, so a file without it, like every existing site, deploys as before), `previews` (`native` for cloudflare and vercel; `cloudflare` or `none` for vps and shared, default `cloudflare`) and the section of the target (`cloudflare`, `vercel`, `vps`, `shared`; unknown keys fail, a missing required field exits 2 naming it). `scripts/deploy/config.mjs --github-output` writes the dispatch of the run to `GITHUB_OUTPUT` (`target`, `effective_target`, `deploy_via` = `wrangler`, `script` or `none`, `secrets`, `preview_fallback`, `needs_lftp`); the YAML only branches on it. The Cloudflare steps run when `deploy_via` is `wrangler` (a cloudflare site on any branch, or the Cloudflare preview of a vps or shared site on a branch); the `Deploy to the site's target` step runs `node scripts/deploy.mjs [--site <slug>] --branch ... --github-output` when it is `script` (vercel on any branch; vps and shared on their production branch only), and `lftp` is installed only for FTPS. The deploy secrets are in the `env` of that one step; the gate sees only booleans. A branch of a vps or shared site with `previews: "none"`, or with the Cloudflare secrets missing, deploys nothing and the sticky comment says the target has no preview. The live report and the comment use `steps.output.outputs.url || steps.target_deploy.outputs.url`.

`scripts/deploy.mjs` (`--site <slug> [--branch B] [--dist D] [--dry-run] [--json] [--github-output] [--rollback] [--print-config]`; modules in `scripts/deploy/`, exit codes 0 ok, 1 refused or failed, 2 bad usage or configuration): a real deploy needs `CI=true` and `GITHUB_ACTIONS=true` and is refused otherwise (exit 1, nothing sent); `--dry-run` prints the target, environment, file count and size, the generated header configuration and the commands without secrets, and changes nothing. Credentials come only from the environment (`VERCEL_TOKEN`, `DEPLOY_SSH_KEY`, `DEPLOY_FTP_PASSWORD`), never an argument, and every printed text passes through `scripts/deploy/redact.mjs`. Tests build fake credentials at runtime. `scripts/deploy/headers.mjs` turns the built `dist/_headers` into `vercel.json`, a Caddy snippet, an Nginx snippet and an `.htaccess`.

- Vercel: the REST API with `fetch` (`/v2/files` by SHA-1, `/v13/deployments`, polling to `READY`; production on the production branch, a preview elsewhere); `VERCEL_API_URL` overrides the base (tests use a local fake; the real API is never called by tests or CI of this repository's tests).
- VPS: rsync over SSH into `releases/<UTC time>-<sha7>/` (hard-linking to `current`), then `ln -sfn` and `mv -T` switch `current` in one step, then prune to `keep` (5) releases; a failed upload removes the half release and never touches `current`; `--rollback` points `current` at the previous release. The server is pinned with the `hostKey` known_hosts line of the configuration, `StrictHostKeyChecking=yes` and no other known_hosts; host key checking is never turned off. The key lives in a 0700 temporary folder, a 0600 file removed afterwards. Remote paths must match a safe alphabet; `/`, `~`, empty, `..` and shallow paths are refused, and `root` as the user too.
- Shared hosting: rsync over SSH with `--delete-after --delay-updates` into a document root that must end in `public_html` (or be listed in `allowPath`), with the generated `.htaccess` staged into the upload and `/.well-known/` kept; with no SSH, FTPS through `lftp` (TLS forced, certificate verified, password only through `LFTP_PASSWORD`); plain FTP is refused.
- The test-only local transport (the "server" is a folder) is a library dependency of the tests, refused unless `NODE_TEST_CONTEXT` is set, with no flag or configuration key to select it. The Vercel target was verified by a real deploy on 2026-10-26 (the owner's `personal-brand` repository); VPS and shared hosting are not verified yet (no accounts): see `docs/status.md`.

## Agent tooling setup

Run `npm run setup:agent` once per machine (or cloud session). It is idempotent: it reads the pins in `agent-tooling.lock.json`, restores any missing design skill under `.claude/skills/`, and turns impeccable telemetry off. `npm run setup:verify` is the fast, offline check; a SessionStart hook in `.claude/settings.json` runs it at every session start and names whatever is missing. `.claude/settings.json` also sets `OPENSPEC_TELEMETRY=0` and allows only safe pipeline commands (npm scripts, `npx astro`, `npx impeccable`, `npx playwright`, `openspec`, read-only git). Telemetry stays off: never run `npx impeccable telemetry on`.

To bump a tool, edit its pin in `agent-tooling.lock.json`, run `FORCE=1 npm run setup:agent`, review the diff and commit. Vendored skill files under `.claude/skills/{ui-ux-pro-max,design-taste-frontend,impeccable}/` are third-party content: never edit them by hand. Their license texts live in `third-party-licenses/` and must be kept.

## MCP servers

Declared in `.mcp.json` (approve them the first time Claude Code asks).

- `astro-docs` (remote, `https://mcp.docs.astro.build/mcp`): look up current Astro APIs, config and integrations before writing Astro code. Prefer it over memory, since Astro moves fast.
- `landing-factory` (local, `node scripts/mcp/server.mjs`): this repository's own agent interface; see "Agent interface". Claude Code asks for approval the first time, like the others.
- `playwright` (`@playwright/mcp`, pinned, `--headless`): open the running dev server or `dist/` preview, take screenshots at 375/768/1440 px, check overflow, console errors and interactions. Use it for visual checks while building; the repeatable QA run lives in `npm run qa` (see QA loop).

`.mcp.json` is portable and does not hard-code a browser path. In a cloud session, where Chromium is preinstalled outside Playwright's default cache, register a local override instead of editing the file, for example:

```bash
claude mcp add --scope local playwright -- npx -y @playwright/mcp@0.0.83 --headless \
  --executable-path /opt/pw-browsers/chromium-1194/chrome-linux/chrome
```

(find the real path with `ls /opt/pw-browsers/chromium-*/chrome-linux/chrome`; add `--no-sandbox` only when running as root in a container). Locally, `npx playwright install chromium` is enough.

## QA loop

`npm run qa` is the single verdict for the quality budgets below. It builds the site, serves `dist/` with `astro preview` on a free port (and always shuts it down), discovers every `dist/**/*.html` page (including noindex ones such as `/islands/`; `404.html` is excluded in `qa.config.json`), and runs:

- full-page screenshots at 375, 768 and 1440 px;
- horizontal overflow and clipped-text detection at each width;
- a `prefers-reduced-motion: reduce` load (at 1440 px): every `[data-reveal]` must be visible, `<html>` must not carry a `lenis` class, and there must be no ScrollTrigger `.pin-spacer`;
- Lighthouse on mobile and desktop (worst of the two per category); performance, accessibility and SEO must be >= 90, best-practices is only reported;
- a motion-enabled load at 1440 px, scrolled through the page (`reveal-end-state`, `--skip reveal-end-state`): after network idle, re-scrolling until reveals settle or the timeout (8 s), every rendered `[data-reveal]` must have computed opacity >= 0.99 and a transform that is `none` or translates by at most 1 px (catches a reveal that hands the element back to the stylesheet's start offset);
- on pages with a 3D scene (`[data-scene]`): a reduced-motion load and a JavaScript-disabled load must show the poster and create no canvas, a normal load at 1440 px scrolled to each scene must create the canvas without console errors or page errors mentioning WebGL, THREE or the scene (scrubbed scenes must also move `data-scene-progress`), and the gzip size of the JS chunks containing Three.js must stay within `threeD.maxGzipKb` (default 200);
- `npx impeccable@4.6.0 detect --json src/`; findings mapped to major/minor/info in `qa.config.json`, and any major finding fails. If the detector cannot run (for example offline on first use), the check fails with the reason; it never passes silently.

Exit code: `0` all checks passed, `1` at least one check failed, `2` the run itself broke (bad config, build error, no Chromium). Options: `npm run qa -- --help` (`--dist <dir>` to skip the build and serve prebuilt HTML, `--skip lighthouse,impeccable`, `--runs 3` for the median of 3 Lighthouse runs, `--config <file>`). Chromium comes from Playwright; set `QA_CHROME_PATH` (or `CHROME_PATH`) to use another binary, for example `/opt/pw-browsers/chromium-*/chrome-linux/chrome` in a cloud session. Thresholds live in `qa.config.json`; with no file the roadmap defaults apply. Never lower a threshold to get a pass.

Output goes to `qa/<ISO-timestamp>/` (colons replaced by `-`) with `report.json`, `report.md` and `screens/<page>-<width>.png`; `qa/latest` is a symlink to the newest run. `qa/` is not committed.

### Reading `report.json`

- `verdict`: `"passed"` or `"failed"`. `skipped` lists checks that were not run.
- `failures[]`: one entry per problem. Fields: `check` (`overflow`, `clipped-text`, `reduced-motion`, `reveal-end-state`, `scene-reduced-motion`, `scene-no-js`, `scene-runtime`, `scene-budget`, `lighthouse`, `impeccable`, `page-load`), `page` (URL path, `null` for impeccable), `viewport` (width in px, or `mobile`/`desktop` for Lighthouse), `metric`, `measured`, `threshold`, `message`, plus `selector` (CSS selector of the offending element), `file` and `line` (impeccable) or `topAudits` (Lighthouse: the highest-impact failing audits).
- `pages[]`: per page, `viewports["375"|"768"|"1440"]` (`documentScrollWidth`, `overflowing[]`, `clipped[]`, `screenshot`), `reducedMotion`, and `lighthouse` (`presets[]` with scores and `topAudits`, `worst` per category).
- `pages[].scenes` (pages with a scene): `names`, `reducedMotion`, `noJs`, `runtime` (per scene: `canvas` created, `state`, `reason`, scrub `progress` samples) and `budget` (`gzipKb`, `maxGzipKb`, `chunks`). `scene-reduced-motion` has metrics `canvas`, `poster` and `three-downloaded`; `scene-no-js` has `poster`; `scene-runtime` has `canvas`, `error` and `scrub`; `scene-budget` has `gzip-kb`. `--skip scenes` skips them.
- `pages[].revealEndState` (null unless the check ran): `viewportWidth`, `pass`, `revealCount` and `offenders[]` (`selector`, `metric` `opacity` or `transform`, `measured`, `text`). `reveal-end-state` failures have metric `opacity` or `transform`.
- `pages[].privacy` (null when the layout check is skipped): taken on the 1440 px normal load after the scroll through the page: `cookies[]` (`name`, `domain`, `path`, `session`, `thirdParty`; never a value), `storage.local[]` and `storage.session[]` (keys only), `thirdPartyHosts[]` (request hosts other than the page's own). The record never changes the QA verdict; the landing report reads it.
- `impeccable`: all findings with `rule`, `severity` (raw), `level` (mapped), `file`, `line`, `snippet`.

### QA -> fix -> QA

1. `npm run qa`, then read `qa/latest/report.json` (`failures` first, `report.md` for a summary) and look at the failing `screens/*.png`.
2. Fix the cause in `src/` (use the `selector`, `file` and `line` fields), never the threshold.
3. Re-run `npm run qa` until the verdict is `passed`. Use `--skip lighthouse,impeccable` for fast layout-only iterations, but the final run must be the full one.

Clipped text that is intentional (for example a truncated card title with `text-overflow: ellipsis`) can be exempted by putting `data-qa-allow-clip` on the element or any ancestor. Use it sparingly and only for deliberate clipping, never to hide a real overflow bug. Pages that are `noindex` skip only Lighthouse's `is-crawlable` audit (`lighthouse.skipCrawlableOnNoindex`); every other SEO audit still counts.

Tests for the QA script itself live in `tests/` (`npm test`). Failing-case fixtures (overflow at 375 px, invisible `[data-reveal]`, clipped text) are tiny static pages in `tests/fixtures/qa/`, served with `--dist`; they are never part of the site build.

## 3D scenes

A landing may use up to two Three.js scenes (`<Scene3D />`, `src/components/three/README.md` has the props and the scene module contract). They are opt-in, built from code (no model files, no R3F), and poster first: the poster is real HTML (the LCP candidate and the fallback), and only when JavaScript runs, WebGL exists, reduced motion is not requested and the figure is within one viewport does the runtime lazy-load Three.js and the scene module after `load` and fade a canvas in. `scrub` links a scene to the scroll progress (0..1) of its section through the motion layer's ScrollTrigger setup. The render loop pauses off-screen and in hidden tabs, DPR is capped (2, or 1.5 under 768 px) and everything is disposed on `astro:before-swap`. Scenes import from `three` by name and read colors from the tokens (`@theme static` keeps every `--color-*` in the CSS). Budgets: 3D JavaScript <= 200 KB gzip per page (`threeD.maxGzipKb`), Lighthouse unchanged. Every scene needs a poster recorded in `assets.json`: render it with `node scripts/render-poster.mjs` (`source: "self"`) or use a credited museum or Commons image. The starter's demo is `/3d/` (noindex, `src/scenes/demo.ts`); `new-site` does not copy it. Historical or cultural pages must not invent quotes or facts: check claims against the museum records of the images used and label myths as such.

## SEO

The factory plans SEO at the brief, writes it at the build and checks it before publishing. It checks markup, not rankings. Guide: `docs/seo.md`.

- **Starter markup.** `BaseLayout` writes the canonical URL, `og:title`, `og:description`, `og:type` (`ogType`), `og:url`, `og:locale`, `og:image` and `twitter:card`, and an optional `jsonLd` prop (object or array) as `<script type="application/ld+json">` with every `<` escaped as `\u003c`. It is the one sanctioned `set:html` (the `injection-sinks` scan skips that exact line). `public/robots.txt` and the `seoFiles()` integration of `astro.config.mjs` give `dist/sitemap.xml` (indexable pages only, read from the built HTML: a page's `noindex` is a layout prop an endpoint cannot see) and the `Sitemap:` line (absolute URLs need `site`). `new-site` copies both; existing sites keep their copies and the report warns until each opts in.
- **Generation.** The `/new-landing` synthesis fills the proposal's "SEO" section (keyword, area, schema type from the brief, else assumed and marked) with `seo-audit` and `schema`; the build writes titles and descriptions within the report limits for every locale, one `h1` per page, the keyword used naturally, and JSON-LD in `src/data/seo.ts` with customer facts only and no review or rating markup without real reviews. Direction pages get a title and description only and no sitemap entry. The final check runs the static report: no `seo-*` item may fail.
- **Out of scope:** keyword research APIs, Search Console, rank tracking, backlinks, `llms.txt`, live-site SEO (claude-seo, kept in mind for landings with traffic).

## Legal compliance

The factory makes legal requirements visible before a landing is published and generates the legal pages a market requires from the customer's own data. **It supports compliance and is not legal advice**: the report, the templates and the docs say so, nothing claims certification, and a lawyer must review the result before it goes live in production.

- **Cookies and trackers (`legal-cookies`).** A known tracker (analytics, ad pixel, session recorder, a video or map embed that sets cookies) loaded unconditionally, or a non-essential cookie or storage key set at first load, fails: consent must come before the cookie (ePrivacy). A tracker that is inert until consent (`<script type="text/plain" data-consent="analytics" src="...">`, or an embed placeholder with `data-consent-src`) passes with a warning to verify the consent mechanism; the report does not judge banners. A page with no cookies, no storage keys and no tracker passes and needs no banner, which is why cookieless analytics (Plausible, Cloudflare Web Analytics) and `youtube-nocookie.com` are preferred. An unclassified cookie or key warns ("classify this cookie") and is never silently passed. The runtime part reads QA's privacy record behind the freshness guard; with no fresh record it is `not-run`.
- **Third-party hosts (`legal-third-party`).** Fonts, styles, scripts or images from a third-party host warn: that host receives the visitor's IP address. Self-host the asset or name the host in the privacy policy.
- **Legal pages (`legal-pages`).** With a brief that names a market with a rule set, the report fails when a page the market requires is missing, a page has no link to it, the page lacks holder data the rule requires, or a `data-legal-pending` marker is still visible. Rule sets: the EU and its member states (privacy policy; holder name and an email or privacy contact) and Spain (LSSI-CE: privacy policy and legal notice; holder name, tax id, address, email; a register entry only warns, since the schema cannot tell a company from a person). No brief, no market or a market without a rule set warns "requirements unknown", never passes. Pages are found by path (`/legal-notice/`, `/aviso-legal/`, `/privacy/`, `/privacidad/`) or by `data-legal-page="notice|privacy"`; `404.html` does not need the footer links.
- **Price claims (`legal-price-claims`).** Discount percentages, struck-through prices and was/now pairs (English and Spanish) warn with the page and the text; for an EU market the fix names the 30-day lowest-price rule. Never a fail: a person judges the claim.
- **Rules and tuning.** Hosts, cookie-name patterns and rule sets live in `scripts/report/legal-rules.mjs`; the `legal` section of `qa.config.json` has `essentialCookies` (default `__cf_bm`, `cf_clearance`), `essentialStorageKeys` and `trackers` (`{ host, category, path? }`, categories `analytics`, `advertising`, `embed`, `cdn`, `cookieless`). Never add a tracker to the allow list to get a pass.
- **Legal pages from the brief.** `node scripts/legal.mjs --site <slug> [--write|--check]` writes `sites/<slug>/src/data/legal.json` (markets, required pages, holder, privacy contact, processing, hosting, third-party hosts of the build, language, `pending`) from `brief.json`; `--check` exits 1 when it is stale, and no market writes nothing. `src/components/legal/{LegalNotice,PrivacyPolicy}.astro` (copied by `new-site`, texts in `texts.ts`, `en` and `es`) render it inside a page of the site; a missing required value renders `<mark data-legal-pending="holder.taxId">` ("pending legal review") and the report fails on it. Holder identity is never assumed or invented. Every legal component source starts with a comment saying the templates are not legal advice. With a multi-locale brief `legal.json` also has `defaultLocale` and `locales[]` (`locale`, `language`, `paths`: `/privacy/`, `/es/privacidad/`, `/legal-notice/`, `/es/aviso-legal/`), the components render in the locale's language (`locale` prop, default `Astro.currentLocale`; `legalPath(data, kind, locale)` gives the footer links), and the report's `legal-pages` item wants each required page in each locale, linked from that locale's own pages (a locale without legal texts gets English and a warning); single-language files keep their old keys.
- **Existing sites** are not edited by this feature: they warn (no market, no brief). tupathdigital gets its legal pages in its own site change once the owner gives the holder data and markets, and its "50% off" claims need review against the 30-day rule.
- **Out of scope for now:** a consent banner component (it arrives with the first change that adds analytics or embeds; until then such a page fails the report), terms of sale, markets other than the EU and Spain, accessibility statements. Guide: `docs/legal.md`.

## AI images

AI-generated images are a fifth, recorded image source (owner decision, 2026-10-24; provider: OpenAI GPT image models). They are for illustration (abstract art, textures, generic objects and scenes) and never pose as real photos of the business, its people or its products.

- **Tool.** `node scripts/ai-images.mjs generate <slug> --prompt "..." --as <name> [--size 1536x1024|1024x1024|1024x1536] [--quality low|medium|high] [--model <id>] [--title ...] [--dry-run]` makes one request to the OpenAI Images API (`scripts/lib/openai-images.mjs`, one `fetch`, no SDK), writes the file to `sites/<slug>/src/assets/images/` and appends the entry to `assets.json`: `source: "ai"`, `generator`, `model`, `prompt`, `revisedPrompt`, `size`, `quality`, `createdAt`, `terms`, `requestId`, `usage`, `credit: false`. `import <slug> <file> --generator ... --model ... --prompt ... --created <date> --terms <url> [--subject owner]` records an image the owner made with their own tool (`imported: true`; all provenance fields required, exit 2 when one is missing; `--subject owner` is the owner portrait, see below). `count <slug>` prints the count, the cap and the consent. Exit codes: 0 ok, 1 refused or failed, 2 bad usage. Run `node scripts/credits.mjs --site <slug>` afterwards.
- **Key and environment.** The key is read only from `OPENAI_API_KEY`; it is never passed as an argument and never printed, logged, stored or placed in an error (errors go through `scripts/report/mask.mjs` and an exact replacement). Real generation needs `OPENAI_API_KEY` as an environment secret and `api.openai.com` in the allowed domains; neither exists in every session, and the skill then falls back to archives. `OPENAI_BASE_URL` overrides the endpoint (tests use a local fake server; the real API is never called by tests or CI). CI never generates images: generated files are committed like any other image.
- **Consent.** `brand.aiImages` in the brief is `allowed`, `not-allowed` or empty, asked by `/brief-intake` and never assumed (validation fails if it is listed in `assumed`). With a brief the tool generates or imports only when it is `allowed` (empty counts as not allowed); with no brief (demo niches) it is allowed.
- **Prompt policy** (`scripts/lib/ai-prompt-policy.mjs`, English and Spanish, no override). Refused with the rule and the reason: the business or a product name from the brief (`brand`), team, staff, customers, founder, owner, testimonials or reviews (`people`), logo or brand mark (`identity`), before and after or results (`results`), a portrait or photo of a named or famous person (`real-person`). Short exclusion clauses (at most 6 words after a negation such as `no`, `without`, `sin`: "No people, no text, no logos.") are not requests and are skipped by the word rules; the brand rule still reads the whole prompt. A false block is fixed by rewording; the filter is best effort and the reviewer's screenshot pass backs it up.
- **Cap.** `qa.config.json` `aiImages` (`provider`, `model` default `gpt-image-1.5`, `size`, `quality`, `maxPerSite` default 12) is validated in `scripts/qa/config.mjs`. A generation at the cap is refused before any request. `--dry-run` prints the request (never the headers) and changes nothing. The default model is confirmed by the first real generation.
- **Owner portrait (personal brands).** The one exception to "AI images never show people", for a business that is a person: `node scripts/ai-images.mjs import <slug> <file> --subject owner ...` (all provenance flags still required) records an AI portrait the owner made with their own tool. Allowed only with a brief that names the business and has `brand.aiImages` and `brand.ownerPortrait` both `allowed` (no brief: refused; `generate` rejects `--subject` with exit 2, so OpenAI generation stays text-only and never makes a face). The entry gets `subject: "owner"` and `imported: true`; for it the prompt policy skips only the `people` and `real-person` rules (`brand`, `identity` and `results` still apply, so the stored prompt must not contain the business name when that is the person's name). Check-landing `ai-provenance` also fails on an owner entry without both consents (or without a brief) and on any `subject` other than `owner`; the `data-ai-disclosure` rule applies as to every AI image. `credits.mjs` lists it under "AI-generated images" noting it is a portrait of the owner made with their consent. In a landing its alt text is "AI-generated portrait of <name>" (never "photo"), and it is never a testimonial or a "photo of the founder".
- **Credits and disclosure.** `credits.mjs` lists AI images under "AI-generated images" (tool and model, date, terms link) and they add no footer credit line. A page that uses any AI image carries a visible `<p data-ai-disclosure>` ("Some images on this page were generated with AI."; `es`: "Algunas imágenes de esta página se generaron con IA.") in its footer. Check-landing `ai-provenance` (only when the manifest has AI entries) fails on a missing provenance field or file, a brief that does not allow AI images, a prompt that breaks the policy, or no visible disclosure on `dist/index.html`; a multi-locale site needs it on every locale's home page, written in that locale's language (`aiDisclosure` of `src/i18n/ui.ts`). OpenAI embeds C2PA metadata in its outputs; the file kept in the repo keeps it, the variants Astro serves may not, so the page disclosure is what covers transparency. Not legal advice (`docs/legal.md`).

## Code quality

QA and the report judge what a landing does; `npm run lint` judges how its code is written. It runs three checks and CI runs it in the `qa` job right after Prettier (the site jobs do not repeat it, since it covers every site).

- **ESLint** (`eslint.config.mjs`, flat config): the recommended rules of `typescript-eslint` and `eslint-plugin-astro` plus the accessibility rules of `eslint-plugin-jsx-a11y` through the Astro plugin, with the TypeScript parser for `.astro` frontmatter (without it every `interface Props` is a parse error). `npm run lint:code` lints `src/` and `sites/*/src/**`; `scripts/`, `tests/` and `openspec/` are out of scope, there are no type-aware rules (`astro check` type-checks) and sites have no ESLint config of their own. No rule is turned off to get a pass; an inline disable comment needs a reason on the same line (`-- reason`); `reportUnusedDisableDirectives` is an error. Astro templates take a block comment `{/* eslint-disable rule -- reason */}` ... `{/* eslint-enable rule */}` (HTML comments and `-next-line` do not apply to attributes).
- **Unused code** (`knip.json`, `npm run lint:unused` = `knip --include files,dependencies --no-config-hints`): fails on a file no page reaches and on a dependency nothing imports, in the root workspace and in each site workspace; unused exports are not reported. Files loaded through `import.meta.glob` are entries (`src/i18n/urls.ts`, `src/scenes/*.ts`): add any new one to `knip.json`. The root workspace also treats `scripts/` and `tests/` as entries (so tooling packages count as used), ignores the starter's legal and i18n components (template source) and lists `eslint-plugin-jsx-a11y` in `ignoreDependencies` (the Astro plugin loads it by name).
- **Optional layers** (`scripts/site-layers.mjs`, exit 0 ok, 1 check failed or refused, 2 bad usage): `new-site` copies the 3D layer (`src/components/three/`, `src/scenes/`, `three`, `@types/three`), the legal components (`src/components/legal/`) and the lead forms components (`src/components/forms/`) into every site. The forms layer `requires` the legal one (a used forms layer keeps the legal components; a layer's own files never make another layer "used"); `add <3d|legal|forms>`. A layer is in use when a file of the site's `src/` outside it imports it (relative specifiers resolved, `three` imported directly counts for 3D, comments ignored; the static scan reuses the export closure's import parsing). `prune --site <slug> [--dry-run]` removes each unused layer and its dependencies (refuses on a non-literal `import()`), then run `npm install` so the lockfile follows; `add <3d|legal> --site <slug>` copies a layer back from the starter (refuses if it exists); `check [--site <slug>]` exits 1 for every site holding an unused layer and never looks at the starter. The `/new-landing` final check prunes, runs `npm install` and `npm run lint`; a lint failure is fixed in the code, never by turning a rule off.
- **Architecture contract** (skill "Code architecture" and `sites/README.md`): section copy and data in typed modules (`src/content/` or `src/data/`), one section per component with an `interface Props` when it takes props, pages only compose, tokens only. Enforced by lint and review, not by a new check.

## Lead forms

A landing can capture leads (a free valuation, a contact or call back request, a quote) through a hosted form service, with no server of ours. Web3Forms is the first provider and a prefilled WhatsApp message is the fallback that needs no account. Guide: `docs/forms.md`. **The forms, the privacy text and the checks support compliance and are not legal advice.**

- **Brief.** The `forms` section (see "Customer brief"). A form needs a legal market and `legal.processing.forms: true`; the customer's `accessKey` (public by design: it can only send mail to its owner) is never invented or assumed. A `web3forms` form without a key renders as the WhatsApp fallback and the report warns.
- **Component.** `src/components/forms/` (a layer, see "Code quality"): `<LeadForm form legal businessName whatsapp thanksHref />` renders a real HTML form that works without JavaScript (a plain POST to `https://api.web3forms.com/submit` with `access_key`, `subject`, `from_name`, `redirect` when `site` is set, the `botcheck` honeypot, a required consent checkbox linking the privacy page); `client.ts` (an Astro-processed module script, never `is:inline`) adds `fetch` with `FormData` (without `redirect`), an `aria-live` status, kept values on error and a 429 message. The `whatsapp` provider builds a `wa.me` message and sends nothing to a server; without JavaScript it is a plain link. Labels and messages are in `fields.ts` (`en`, `es`). `ThankYou.astro` is the `noindex` thank-you page. The starter's demo is `/forms/` (`noindex`; fake access key and fixture holder in `src/pages/forms/_demo.ts`).
- **CSP.** `astro.config.mjs` reads `src/data/legal.json`: only a site whose forms use Web3Forms adds `https://api.web3forms.com` (and nothing else) to `form-action` and `connect-src`. A site without such a form, and the starter, gains no origin. `public/_headers` is unchanged.
- **Legal.** `legal.mjs` writes `processing.forms` as `{ provider, providers, purposes, fields }` (a key-less web3forms form counts as WhatsApp; an older `true` keeps rendering the old sentence). The privacy policy names Web3Forms (Web3Creative, India), the US servers as an international transfer, what is sent, why, that submissions are forwarded and not stored by the provider (logs about two months) and that the holder keeps the request as long as needed.
- **Report.** `legal-forms` (area `legal`): fails without a required consent checkbox linking a privacy page of the site, for a host outside `report.forms.providers` (default `["api.web3forms.com"]`, in `qa.config.json`, validated; never add a host to get a pass) or over plain HTTP, when the privacy page does not name the provider, or when a Web3Forms form has no `access_key`; warns on a WhatsApp fallback; `na` without forms.
- **Production.** A `*.pages.dev` preview may not deliver (some free subdomains are blocked); production forms need the customer's domain. The first real submission is a manual check by the owner with his own key (`docs/status.md`). Tests and CI never call Web3Forms (a local fake endpoint and browser interception).
- **Out of scope:** our own backend or serverless function, storing submissions, a CRM, file uploads, a captcha (hCaptcha is a later option), double opt-in, analytics on submissions, other providers.

## Quality budgets

A landing is done only when all of these hold:

- Lighthouse >= 90 in performance, accessibility and SEO
- No horizontal overflow at 375, 768 and 1440 px
- `prefers-reduced-motion` respected: no smooth scroll, pin or parallax; reveal content is visible
- Content is visible and usable without JavaScript (a 3D scene shows its poster)
- Original copy and assets; no major findings in impeccable detect
- The landing report (`npm run report`) has no failing item: headers, private files, secrets, `npm audit`, SRI, mixed content, broken links, and the legal area (tracker or non-essential cookie without consent, a legal page the market requires, a pending-review marker)

Motion rules: pages are static HTML by default; load GSAP/Lenis only through `<Motion />`; load Three.js only through `<Scene3D />`; hydrate React only with an explicit `client:*` directive.

## Design archetypes

`design-archetypes/` holds 10 composition archetype sheets (layout grammar, header and footer, typography, imagery, buttons, motion, lendable traits, do and don't, expected layout-signature ranges) and a README with the closed vocabularies of requirement `signals` and lendable `traits`. They exist because every landing shared one composition; they are a **starting grammar, not a template**.

- The synthesis writes a `Signals:` line in the proposal Brief and runs `node scripts/pick-archetypes.mjs --site <slug>`. It ranks blends (one primary that owns the grammar, at most one secondary lending one or two traits) from the signals and from the reference sheets (`--refs`, else those named in `RUN.md` and `PROPOSAL.md`), excludes blends other sites already use (`archetype:` in their `landing-meta`; a primary used by two other sites is excluded) and may offer `archetype: custom` when the references clearly lead. The chosen blend, a twist from the requirement and the reasons go in the proposal's "Archetype blend" and in `landing-meta`.
- The build may deviate from any archetype rule when the requirement or a reference justifies it; each deviation is written in `RUN.md` "Design decisions". The archetype `signature` comparison is only a warning. The hard rules stay the quality budgets, licensing and originality, and the layout diversity rule.
- `scripts/layout-signature.mjs` measures the built home page (columns per section, full-bleed share, radii, button shape, heading scale and alignment, eyebrow share, density, footer type, rotation and overlap, sticky or pinned elements) and perceptual hashes of the viewport slices; `check-landing` compares it with every other site. On a multi-locale site it measures the default locale's home page (`/`) only, since the other locales share its components. QA discovers every `dist/**/*.html`, so each locale's pages get the same overflow, reduced-motion and Lighthouse checks. No generated site is a model for another: never point a landing's instructions or templates at another site.

## Extract patterns, don't clone

References are for learning patterns, never for copying. From a reference site, keep only an abstract pattern sheet in `patterns/` (structure, rhythm, interaction, motion behavior in your own words).

NEVER extract, download, store, reuse or publish from a reference site:

- images or photographs
- videos
- 3D models
- logos or brand marks
- copy (headlines, body text, microcopy)
- illustrations or icons it created
- literal code (markup, CSS, JS, shaders), even if minified or lightly edited

Landings use original copy and original or properly licensed assets.

### Analyzing a reference: `/analyze-reference`

Use the `analyze-reference` skill (`.claude/skills/analyze-reference/SKILL.md`) for every reference; do not browse and take notes by hand.

```text
/analyze-reference <url> [--focus "what we like"]    # optionally 1-2 internal links of the same site
```

Pipeline: `check-robots.mjs` (robots.txt for `*`, ClaudeBot, anthropic-ai, GPTBot, `X-Robots-Tag`, meta robots, TDM reservation; any disallow, reservation or unverifiable check aborts with no sheet) -> `recon.mjs` (Playwright; writes `.cache/analyze/<slug>/recon.json` and screenshots at 375/768/1440) -> you read the JSON and look at the screenshots -> write `patterns/<slug>.md` from `patterns/_template.md` in abstract terms -> `npm run validate:patterns` -> `recon.mjs --cleanup <slug>`, which always runs, even after an abort or error.

Where things go: sheets in `patterns/<slug>.md` (versioned, reviewed in the PR; `patterns/_example-starter-demo.md` is a model); temporary working files only in `.cache/analyze/` (git-ignored, deleted at the end). Never write colors as codes, name brand fonts, quote copy beyond 12 words, link media files or paste code in a sheet; the validator enforces this and a human reviews it. Never try to bypass a login, bot challenge or block. Pages that scroll an inner container (document one viewport tall) are handled by `recon.mjs`: it detects the scroller and records `scroller.kind` (`document` or `container`) in `recon.json`. Behind `HTTPS_PROXY`/`HTTP_PROXY` (cloud sessions) `check-robots.mjs` and `recon.mjs` route through the proxy on their own; never set `NODE_USE_ENV_PROXY` by hand. Optional REA (`npx rea-agents analyze-javascript-application`) only to explain an effect recon cannot identify, and only its written conclusion goes in the sheet. Guidance, not legal advice. The recon approach is adapted from JCodesMore/ai-website-cloner-template (MIT).

## Licensing and credits

Every external image, font, icon or component must have a compatible license (for example CC0, MIT, or an open collection that allows commercial use). Record each one in a `CREDITS.md` at the root of the site's repo: source URL, author, license. No asset without a recorded license. An AI-generated image has no author or source page: it is recorded in `assets.json` with its generator, model, prompt, date and a link to the generator's terms, listed under "AI-generated images" in `CREDITS.md`, and disclosed on the page (see "AI images").

## Scope discipline

Do not add a shared component package across sites (sites copy the starter), per-site custom domains, CMS, i18n beyond opt-in multi-locale landings (a landing with two or more languages through `new-site --langs`; no browser-language redirect, right-to-left layouts, per-locale domains or custom locale paths), client/commercial licensing features, a backend of our own for forms (hosted form services through the forms layer are in scope, see "Lead forms") or a consent banner component (until a change adds analytics or embeds): they are out of scope. Do not commit generated output (`dist/`, `.astro/`, `qa/`).
