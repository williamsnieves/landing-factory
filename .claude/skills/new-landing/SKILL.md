# new-landing

One command, one landing. This skill is the orchestrator: it runs the phases below in order, delegates the design system, build and QA to subagents (one design skill each), and writes every phase result to disk so a run can resume. It never edits another site, the root starter, or the vendored skills under `.claude/skills/{ui-ux-pro-max,design-taste-frontend,impeccable}/`.

Read `CLAUDE.md` first (language, extract-patterns-don't-clone, licensing, quality budgets, QA loop). No generated site is a model for another: structure comes from the archetype sheets in `design-archetypes/` (read its README) and from the reference sheets, never from copying a site in `sites/`.

**Archetypes are a starting grammar, not a template.** The build may deviate from any archetype rule when the requirement or a reference justifies it; every deviation is written in RUN.md "Design decisions". The only hard rules are the quality budgets, licensing and originality, and the layout diversity rule of the final check. The archetype `signature` comparison is a warning, never a failure. All files, comments and RUN.md entries are in English; the page copy is in `--lang` (default `es`).

## Arguments

`<slug>` (required, `^[a-z0-9]+(-[a-z0-9]+)*$`), `--niche "..."` (required unless a brief exists), `--brief sites/<slug>/brief.json` (the customer requirement written by `/brief-intake` or by hand; see "Brief file" below), `--refs a,b` (slugs of `patterns/<slug>.md`, 0 to 3), `--auto` (do not stop at the checkpoint), `--dry-run` (stop after the design system), `--resume`, `--max-attempts N` (default 5), `--lang` (default `es`), `--langs a,b` (a multi-locale landing, see "Languages"), `--sources commons,met` (image sources, default `commons`; use `met` for historical or cultural niches), `--directions` (build visual directions instead of the landing, see "Directions run"), `--count 2|3` (how many, default 3, only with `--directions`).

`scripts/new-landing.sh` has already run the preflight and `npm run new-site -- <slug>`, so `sites/<slug>/` exists with `PROPOSAL.md`, `RUN.md` and `assets.json` templates. If it does not (the skill was typed by hand), run `node scripts/preflight.mjs --slug <slug>` and `npm run new-site -- <slug> --lang <lang>` then `npm install --no-audit --no-fund`, and stop on any failure with its message.

**Brief file.** When `sites/<slug>/brief.json` exists (`scripts/new-landing.sh --brief <file>` copies it there and has already run `node scripts/brief.mjs validate`; with `--brief` and no `--niche`, `business.description` is the niche), it is the requirement: the customer's own words and facts. Run `node scripts/brief.mjs validate --site <slug>` once more and stop with its errors if it fails (set `Result: failed`, no further phase). Read it with `node scripts/brief.mjs summary --site <slug>` and the JSON itself. Fields listed in `assumed` and fields that are empty are **not customer facts**; everything else is, and the page must show it exactly (the final check `brief-facts` verifies business name, primary call-to-action URL, contact email and phone, each product name and price on the built page). Without a brief, today's behavior stays: the niche alone, every decision assumed.

**Languages.** A landing is single-language unless the brief has `languages` with two or more tags (or `--langs a,b` was given). `scripts/new-landing.sh` then ran `npm run new-site -- <slug> --lang <default> --langs <list>`, so the site is multi-locale: `astro.config.mjs` has Astro's `i18n` block (default locale at the root, the others under `/<locale>/`), `src/pages/<locale>/index.astro` exists for each other locale, `src/i18n/ui.ts` holds the typed UI dictionary with `t(locale)`, and `src/components/i18n/LanguageSwitcher.astro` is copied. See "Multi-locale landings" in the build phase. A single-language run ignores all of this.

Headless runs (`claude -p`) cannot ask questions: make a sensible choice, and write it in the proposal under Decisions as "Assumed: ... (confirm at the checkpoint)".

Run every subagent and every long command in the **foreground** (Agent tool with `run_in_background: false`, Bash without `run_in_background`) and wait for its result before the next step. In `claude -p` the run ends as soon as you end your turn, and background work left running is stopped; never end a turn to "wait for a report". The run is finished only when RUN.md has its final `Result:`.

## Run log and resume rules

`sites/<slug>/RUN.md` is the state. Before each phase set its row in the Phases table to `in-progress` with the start time, and at the end to `done` (or `failed`) with the finish time and a one-line note. Get timestamps with `date -u +%Y-%m-%dT%H:%M:%SZ`. The `Result:` line near the top is read by `scripts/new-landing.sh` for its exit code: `checkpoint`, `dry-run-done`, `directions`, `passed` or `failed`.

With `--resume` (or when RUN.md already has finished phases), skip a phase only when its row is `done` AND its artifact exists:

| Phase         | Artifact that must exist                                                                                      |
| ------------- | ------------------------------------------------------------------------------------------------------------- |
| brief         | RUN.md Inputs table filled (with a brief: its path, and the lists of assumed and empty fields)                |
| synthesis     | `PROPOSAL.md` with no empty section, a `Signals:` line, an "Archetype blend" section and `Status:` no longer `draft` |
| checkpoint    | passed when `--auto` or `--dry-run` is given, or the user re-ran with `--resume --auto`                       |
| design-system | `design-system/<slug>/MASTER.md` with a valid `landing-meta` block (including `archetype`), and the site's `tokens.css` derived from it |
| build         | a real `src/pages/index.astro` (no `noindex`), `assets.json` with images, `node scripts/credits.mjs --site <slug> --check` passing |
| qa            | `qa/<slug>/latest/report.json` with verdict `passed`                                                          |
| polish        | row `done`                                                                                                    |
| final-check   | row `done` and `sites/<slug>/layout-signature.json` written                                                    |

A row left `in-progress` or an artifact that is missing means: redo that phase from its start, keeping the files that are already good. Never delete the user's edits to `PROPOSAL.md`: on resume, the proposal on disk is the approved plan.

## Directions run (`--directions`)

A cheap way to show the customer what the landing could look like before the full build (cost and time are a fraction of a build). With `--directions`, run only the Brief phase, the signals part of the Synthesis, and the steps below, then set `Result: directions` and stop. No `PROPOSAL.md` page map, no design-system `MASTER.md`, no design-taste-frontend, no impeccable polish, no layout signature and no final check. Rows of RUN.md use the phases `brief`, `directions`, `qa`.

1. Brief: as in phase 1.
2. Signals and references only: write the `Signals:` line (as in phase 2) and run `node scripts/pick-archetypes.mjs --site <slug> --top 8 --json`. Choose `--count` blends (default 3) whose **primary archetypes all differ**; a `custom` blend counts as its own primary. Prefer the top candidates; the blends that other sites use are already excluded.
3. One subagent per direction, `a`, `b`, `c` in order, each using **ui-ux-pro-max only** (not design-taste-frontend, not impeccable). Each direction lives inside the site, scoped by page, so one build serves all of them:
   - the page `src/pages/directions/<id>/index.astro`: `BaseLayout` with `noindex`, a root element carrying `data-direction="<id>"`, a hero and **one** section built from the brief's real copy (business name, offer, prices, calls to action with their real URLs; assumed or empty fields stay placeholders and are not presented as customer facts), in the language of the page;
   - the stylesheet `src/styles/directions/<id>.css`, imported by that page only: it redefines the token variables (`--color-*`, `--font-*`, radii) under `[data-direction="<id>"]` and imports its own `@fontsource` packages (installed with the exact `npm install -w site-<slug> @fontsource-variable/<name>` form of phase 4); the tokens of `tokens.css` stay the neutral defaults. Palette and fonts come from ui-ux-pro-max (`python3 .claude/skills/ui-ux-pro-max/scripts/search.py "<niche + direction keywords>" --design-system -p "<Brand>"`), obey the brief's brand constraints, and meet the contrast rules (text >= 4.5);
   - a `title` and a `description` within the report's limits (title 30 to 60 characters, description 70 to 160) in the page's language; no JSON-LD and no sitemap entry for direction pages: they stay `noindex` and the sitemap skips them;
   - sections in `src/components/directions/<id>/`, one component each, with an `interface Props` when they take props;
   - images only from the usual sources (the customer's files, Commons and The Met through `node scripts/find-images.mjs`, AI only where the "AI images" rules allow it), recorded in `assets.json`; no motion beyond reveals;
   - the direction's palette and fonts are written in `DIRECTIONS.md` as a short MASTER-style block (not as `design-system/<slug>/MASTER.md`).
4. The home page `src/pages/index.astro` becomes a `noindex` index: one link per direction with its one-line idea, and a note that these are draft directions. Every direction page and the index follow the 404 rule: readable at 375 px.
5. `node scripts/credits.mjs --site <slug>`.
6. Write `sites/<slug>/directions.json` (version 1; per direction `id`, `archetype`, `traits`, `primary`, `displayFont`, `bodyFont`, `hero`, `idea`; `choice: null`; see `scripts/lib/directions-schema.mjs`) and `sites/<slug>/DIRECTIONS.md` (one paragraph and the blend per direction, the palette and fonts block, and the run's cost from the usage line).
7. QA loop as in phase 6 (`npm run qa -- --site <slug>` until it passes or attempts run out; each direction page gets the usual checks).
8. `node scripts/directions.mjs check --site <slug>` must pass (2 or 3 directions, different primary archetypes, no shared trio of primary color family, display font and hero type, every page built and `noindex`). Fix the directions, never the check.
9. Set `Result: directions`, mark the rows `done`, write Totals. Never choose for the customer: the owner or the agent records the choice with `node scripts/directions.mjs choose --site <slug> --direction <id> [--notes "..."]`.

**Resume after the choice.** When `sites/<slug>/directions.json` exists and the run is not `--directions`:

- with `choice: null`, stop at once with `Result: failed` and the message "no direction chosen: run node scripts/directions.mjs choose" (`scripts/new-landing.sh` already refuses);
- with a choice, treat it as approved input: the proposal's "Archetype blend" is the chosen direction's `archetype` and `traits` (no new `pick-archetypes` choice; the twist and reasons are still written), the design system starts from the chosen palette and fonts (ui-ux-pro-max may refine them; every conflict is listed in MASTER.md), and the customer's `choice.notes` are fixed inputs written under Decisions in the proposal, in the customer's words, never invented or softened;
- before the build, remove `src/pages/directions/`, `src/styles/directions/`, `src/components/directions/`, the `@fontsource` packages only the rejected directions used (and their CREDITS.md font rows), and replace the index page with the real home page. Drop from `assets.json` the images of the rejected directions that the build does not reuse, then run `node scripts/credits.mjs --site <slug>`;
- keep `directions.json` and `DIRECTIONS.md` as the record. A site without `directions.json` builds exactly as before.

## Prospect landings (`prospect.status` is `prospect`)

A brief with `prospect.status: "prospect"` describes a business that has not bought anything: the page is a design proposal the owner shows it. Design: `openspec/changes/add-prospect-landings/design.md`; guide: `docs/prospect.md`. A brief without the section, or with `status: "sold"`, builds as usual.

- **Facts and sources.** The brief's facts are public data read by hand, each backed by a `prospect.sources` entry (https URL, retrieval date) or listed in `assumed`. The proposal gets a section "Prospect: facts and sources" with every fact, its source URL and date, and every assumed value with its reason. Never read the prospect's own site here (`analyze-reference` is for design references only) and never add a fact the brief does not have.
- **No brand, no consent.** Use no logo, photo, color or font of the business (the brief cannot list any). Images come from Commons and The Met only (`find-images.mjs`, `--sources commons,met` when the niche fits); no AI images, no owner portrait, no lead forms and no legal holder: nobody has agreed to them. Palette and fonts are picked from the niche with ui-ux-pro-max only, never from the prospect's look, and Decisions in the proposal and RUN.md say so.
- **Before the build** run `node scripts/prospect.mjs write --site <slug>`: it writes `src/data/prospect.json`, which makes `BaseLayout` add `noindex` and the visible `data-prospect-notice` to every page, and `astro.config.mjs` write an empty sitemap and the `X-Robots-Tag: noindex` header. Do not remove, hide or restyle the notice away (it is a `role="note"` strip at the top of `<main>`), and do not add `noindex`, a sitemap or a header by hand.
- **Final check.** `check-landing` runs the `prospect` rule (every page `noindex` with the notice naming the business, no sitemap URL, the header, no customer or AI image in `assets.json`, every fact sourced or assumed, `prospect.json` current). Fix the site, never the brief or the rule.
- **At the end**, after RUN.md says `Result: passed`, run `node scripts/prospect.mjs kit --site <slug>`: it writes `sites/<slug>/SALES.md` (what was built, facts and sources, assumed values, what going live needs, talking points). It holds no message to the prospect; do not write one. Mention `SALES.md` in RUN.md.

## Phases

### 1. Brief

Fill the RUN.md Inputs table (niche, brief path, references, mode, max attempts, start time).

Without a brief: decide goal, audience, tone and language from the niche. Read each `--refs` sheet in `patterns/`. If no refs are given, read `patterns/README.md` and pick up to two generic sheets that fit the niche, or none.

With a brief: goal, audience, tone and language come from it (`goal`, `audience`, `tone`, `language`), not from your own guess; note in the Inputs table which fields are `assumed` and which recommended ones are empty. The run's references are the `references.liked[].sheet` values (pass them to `pick-archetypes` with `--refs`), plus any `--refs` given; read those sheets in `patterns/`. A liked URL without a sheet is listed in the proposal as "to analyze" (suggest `/analyze-reference <url>`) and is not read here. If neither the brief nor `--refs` names a sheet, pick up to two generic sheets as without a brief, or none. `references.disliked` entries become "avoid" notes (see Synthesis). Local assets the brief names (`assets[].path`, relative to `sites/<slug>/`) are listed under Inputs with their `kind`; links that need a login (a private cloud folder, for example) are written in RUN.md under "To fetch by the owner" and are never accessed around their access control.

### 2. Synthesis

Write `sites/<slug>/PROPOSAL.md` from the template already in the folder; keep its headings. The template is neutral: fill it from this brief and the references, not from another site.

- Brand: with a brief, `business.name`, city, country and description are the customer's; use them as they are. Without one, a fictional business name and city if the niche gives none. Contact data comes from `contact` in the brief; whatever is empty or assumed is a placeholder and the proposal says so.
- Offer, audience, goal and tone (with a brief): the products with their names, prices, currency and links come from `offer`; the audience from `audience`; the one conversion action and its real URL from `goal.primary` (and `goal.secondary` as the quiet one); tone words from `tone`. Do not rename products, change prices or add products, reviews, ratings or results the customer did not give. Brand constraints (`brand.colors`, `brand.fonts`, `brand.keep`, `brand.avoid`) are fixed inputs for the design system step, not suggestions. `legal.notices` adds the required notices to the page map (footer or a legal section) and, when `regulated` is true, applies the regulated-niche rule below. `legal.markets` decides the legal pages (see "Legal pages" in the build phase): when it is non-empty, add the legal notice and privacy policy pages its rule set requires to the page map, each linked from every page footer. When it is empty (or there is no brief), no legal page is added and Decisions says "Legal requirements unknown: the brief names no market".
- Lead forms (with a brief): each entry of `forms` goes into the page map where the proposal puts it (a `valuation` form next to the hero's call to action or in its own section, a `contact` form in the contact section); name the form, its purpose and its fields. A `web3forms` form without an `accessKey` falls back to a WhatsApp message (needs `contact.phone` or the primary action's wa.me link): keep the WhatsApp call to action as the primary one and list the missing key under Decisions and in RUN.md "to confirm before launch". A brief with forms always has a market and `legal.processing.forms: true` (validation enforces it), so the privacy policy page is in the page map. See "Lead forms" in the build phase.
- References: a table of what is taken from each sheet (name it as `patterns/<slug>.md` so `pick-archetypes` finds it) and what is left, plus a "Direction in one line". With a brief, put the customer's reason from `references.liked[].why` next to the sheet, list liked URLs without a sheet as "to analyze", and put each `references.disliked` entry (with its `why`) under "What we leave" as something to avoid.
- Page map: 7 to 10 sections with height, purpose and layout idea. One conversion action named in the brief, repeated in header, a mid-page block and the closing section.
- Motion plan: only primitives in `sites/<slug>/src/components/motion/README.md` (reveal, pin, parallax, ...). At most one pinned section and one playful moment. State the reduced-motion and no-JS behavior.
- Visual direction: type and palette in words (the design system step fixes values), the hero type (one of `full-bleed-photo`, `split`, `typographic`, `video`, `illustration`, `collage`) and the imagery plan (the customer's files first, then photos from Commons and, for historical or cultural niches, The Met; AI illustrations only where the "AI images" rules below allow them, each planned image tagged with its source).
- Signals and archetype blend (this is what steers the layout): 1) In the Brief, write one line `Signals: a, b, c` using only the closed vocabulary of `design-archetypes/README.md` (personality, audience, offer, tone, and the assets available: `photo-rich` or `few-assets`). With a brief, derive them from it: `business.kind`, `tone`, `offer` and `audience` map onto the vocabulary (for example a single product or a product line is `product-showcase`, a business tied to an address and hours is `local-service`, one obvious action is `conversion-first`), and the assets signal is `photo-rich` when the brief lists 5 or more photos (`assets[].kind: photo`) and `few-assets` otherwise. 2) Run `node scripts/pick-archetypes.mjs --site <slug>` (it reads the signals, the reference sheets named in RUN.md and the References table, and skips blends other sites already use; `--refs a,b` overrides the sheets). 3) Read the sheets of the candidates in `design-archetypes/` and choose one blend: prefer the top candidate unless the brief clearly argues otherwise, and say why in one or two sentences. 4) A clear reference direction can lead instead: the candidate list then offers `archetype: custom`; choose it only when the references give the layout grammar, and write which reference drives which part (archetypes only fill gaps). 5) Add one twist that comes from the requirement itself (a product's texture, a ritual of the business, a number the customer is proud of). 6) Fill the "Archetype blend" section of the proposal: primary, secondary, the one or two lent traits (and any `ref:<sheet>/<trait>`), the signals that led there, the twist, and the deviations you already plan. The blend is recorded again in `landing-meta` (`archetype`, `traits`).
- Diversity: list the other sites' choices with `grep -A8 landing-meta design-system/*/MASTER.md` and pick a primary color family, display font and hero type that do not repeat any single site's trio; prefer differing in all three. The final check also compares the built layout with every other site (`layout-diversity`), so a new palette on the same composition fails.
- SEO: fill the "SEO" section of the proposal. Read `.claude/skills/seo-audit/SKILL.md` (and `references/local-seo.md` when the business has an address or a service area) and `.claude/skills/schema/SKILL.md`; those skills mention `.agents/product-marketing.md`, which does not exist here, so the brief is the context. With a brief, the primary keyword, service area and schema type come from `seo.primaryKeyword`, `seo.serviceArea` and `seo.schemaType`; when they are empty, choose them from the niche and the offer and mark each as assumed under Decisions (never present a chosen keyword as the customer's). Name which `seo-audit` rules apply (local business or not) and the title and description limits of the report (`report.seo` in `qa.config.json`: title 30 to 60 characters, description 70 to 160). Do not invent search volumes, rankings or an area the customer did not name.
- Regulated niches (health, dental, legal, finance, supplements): the copy makes no promise of results, no diagnosis or treatment claims, no invented reviews, ratings, testimonials, awards, certifications or "years of experience" figures. Say in Decisions what the page does instead (services described plainly, "ask us" calls to action).
- 3D: fill the "3D" section of the proposal. Default is none. A niche may plan at most two scenes (`<Scene3D />`, see `sites/<slug>/src/components/three/README.md`) when 3D tells the story (an object that turns with the scroll, a field of particles); each scene states its purpose, its poster, its scroll behavior and its reduced-motion fallback (the poster). Never plan a scene for decoration only, and never plan external 3D models: scenes are built from code.
- Historical or cultural niches (history, martial arts, museums, crafts, religion): the copy must be historically careful. No invented quotes or attributions, no dates or facts that the sources used do not support (check them against the museum records of the images you use), myths and legends labeled as such, no romanticized claims presented as fact. List the sources (museum object pages) in the proposal. Plan images from `--sources met` as well as Commons.
- Legal, under Decisions: with markets, list the legal pages the market requires and every value still `pending` (`node scripts/legal.mjs --site <slug>` prints them; holder identity is never assumed or invented); without markets or without a brief, write "legal requirements unknown". Never present the pages as legal advice or as a certification.
- Add to Decisions: without a brief, the page uses stock photos and sample data to replace before launch. With a brief, list every `assumed` field with its reason and every recommended field that is empty and that the page needs, each with the placeholder used ("Assumed: ... (confirm at the checkpoint)"); customer facts are never called sample, example or placeholder, and only the placeholders are labeled as such on the page. Also list the customer's assets and where each is used, and stock photos only where the customer has none.

Run `npx prettier --write sites/<slug>/PROPOSAL.md`, check that `node scripts/pick-archetypes.mjs --site <slug> --top 1` still reads the `Signals:` line, set `Status: **proposed**` in it, mark synthesis `done`.

### 3. Checkpoint

If neither `--auto` nor `--dry-run` was given: set `Result: checkpoint` in RUN.md, mark the checkpoint row `waiting`, print the path of `PROPOSAL.md`, and stop. Do not write any code. The user reviews and continues with `scripts/new-landing.sh <slug> --niche "..." --resume --auto` (with a brief: `--brief sites/<slug>/brief.json` instead of `--niche`). Otherwise mark it `done` and continue.

### 4. Design system (subagent, ui-ux-pro-max only)

Spawn a subagent with this brief: the `Direction in one line` and the Visual direction section of the proposal, the "Archetype blend" section with the sheets of the chosen primary and secondary archetypes (and the reference sheets for a `custom` blend), the niche, the language, the other sites' `landing-meta` to avoid, and the instruction to use only the `ui-ux-pro-max` skill (not design-taste-frontend, not impeccable). It must:

1. Query the skill with the direction, not just the niche: `python3 .claude/skills/ui-ux-pro-max/scripts/search.py "<niche + direction keywords>" --design-system -p "<Brand>"`, then `--domain color`, `--domain typography`, `--domain style`. Record the queries.
2. Write `design-system/<slug>/MASTER.md` following the headings of `design-system/_template.md`: queries run, conflicts between the skill and the proposal (the approved proposal wins; list each), chosen style, a Palette section whose table holds every color as `#RRGGBB` plus the WCAG contrast of each pair used (text >= 4.5, large text and non-text >= 3; do not compute ratios by hand: `node scripts/check-landing.mjs --site <slug>` checks the standard text pairs of `tokens.css` and names any pair under 4.5), typography (open-licensed families that exist as `@fontsource-variable/<name>`, or `@fontsource/<name>`; check with `npm view <package> version`), type scale, spacing and radii, motion tokens, do/don't for the build, and a final fenced block. ui-ux-pro-max still owns palette and fonts; the archetype sheets constrain the radius family, the type contrast between heading and body, and the density tokens (a Swiss or brutalist blend means near-zero radii and flush-left type, a collage or local-service blend may round), and the conflicts section lists any place where the skill's style disagrees with them:

   ````
   ```landing-meta
   primary: #rrggbb
   display-font: Family
   body-font: Family
   hero: full-bleed-photo
   archetype: primary+secondary
   traits: lent-trait-a, lent-trait-b
   ```
   ````

   `archetype` and `traits` repeat the proposal's blend (`custom` and `ref:<sheet>/<trait>` are valid).

3. Translate it into `sites/<slug>/src/styles/tokens.css` (edit the file the scaffold copied from the starter and keep its shape: `@theme static` colors (keep `static`, so 3D scenes can read every color token), fonts, type scale, spacing, radii, motion) and the font imports in `src/styles/global.css`. Install the font packages with exactly `npm install -w site-<slug> @fontsource-variable/<name> [@fontsource-variable/<other>]` (or `@fontsource/<name>`): only this form, with `-w` first and no other flags, is allowed in automatic mode. Add each font to the fonts table in `sites/<slug>/CREDITS.md` (source URL, author, SIL OFL 1.1).
4. Verify: `node scripts/check-landing.mjs --site <slug> --json` shows `tokens`, `contrast`, `landing-meta` and `diversity` ok (`layout-diversity` needs the built page and runs in the final check) (other checks may still fail before the build). Fix MASTER.md or tokens until they are.

Mark the phase `done`. With `--dry-run`: set `Result: dry-run-done`, write the Totals section and stop here.

### 5. Build (subagent, design-taste-frontend for art direction)

### 6. QA loop (subagent)

`--max-attempts N` is the number of fix-and-rerun rounds after the first run, so QA runs at most N + 1 times (N = 0: one run, no fixes).

Each attempt: `npm run qa -- --site <slug>`. If it exits 2 with "Chromium not found", run `node scripts/preflight.mjs --chromium-path` and retry with `QA_CHROME_PATH=<that path>` in front. Read `qa/<slug>/latest/report.json` (`failures` first) and the failing `screens/*.png`. Exit 0 ends the loop. Otherwise fix the cause in `sites/<slug>/src/` using each failure's `selector`, `file` and `line`, in this order: overflow, clipped text, reduced motion, accessibility, SEO, performance, impeccable. Pages with a scene also get the 3D checks (`scene-reduced-motion`, `scene-no-js`, `scene-runtime`, `scene-budget` in `report.json`): a canvas under reduced motion, a missing poster, a console or page error mentioning WebGL, THREE or the scene, or 3D JavaScript over budget fails the run; fix the scene, not the threshold. Never lower a threshold in `qa.config.json`. Append a row to the RUN.md QA attempts table: number, verdict, failure counts by check, what was fixed.

If attempts run out: write the remaining failures (check, page, metric, message) under QA attempts, set `Result: failed`, mark qa `failed`, write Totals and stop. Do not polish a failing site.

After a pass, look at the result like a reviewer. Full-page screenshots show pinned sections as empty space and hide per-viewport problems, so run `node scripts/section-shots.mjs --site <slug>` (it serves `sites/<slug>/dist` itself and always stops its server) and open the images in `qa/<slug>/sections/` with the Read tool: one viewport per section (`section[id]`, header, footer) at 375, 768 and 1440 px. Check: repeated photos, photo-text mismatch, cramped, clipped or overlapping type, unreadable contrast over images, empty areas. Look at the 404 page too: `node scripts/section-shots.mjs --site <slug> --include-404` also captures `404.html` (files `404-html-*` in the same folder); it must be restyled in the landing's design, readable at 375 px and link home and to the primary call to action. Fix findings and re-run QA (counts as an attempt). Never leave a server running: do not start `astro preview` or `astro dev` by hand; if you must, run it as a background task and stop it with the task tool.

Known fixes from earlier runs:
- Do: `aria-label` on a table instead of an `sr-only` caption (QA flags the caption as clipped text).
- Do: put `data-qa-allow-clip` only on a deliberately clipped marquee word, never to hide an overflow bug.
- Do: outlined giant type with `-webkit-text-stroke` on a variable font: fill with the page color and use a doubled stroke with `paint-order: stroke fill` to avoid overlapping contours.
- Do: wrap giant or wordmark type in `overflow-x: clip` and check 375, 768 and 1440 px.
- Don't: use one photo a third time to fill a gap; search another.
- Don't: trust a green QA as "done"; it does not see repeated or wrong photos.
- Don't: leave `astro preview` or other server processes running.

### 7. Polish (impeccable, once)

Mark polish `in-progress`. Run `npx impeccable@4.6.0 detect sites/<slug>/src` and the impeccable critique on the built page; apply only findings that clearly improve hierarchy, copy, spacing or accessibility, with small edits that keep tokens and the proposal intact. Re-run `npm run qa -- --site <slug>`; if the polish turned QA red, undo the edit that caused it. One polish round only.

### 8. Final check

Run, and fix until all pass:

1. Layers and lint: `node scripts/site-layers.mjs prune --site <slug>` (removes the 3D layer, the legal components and the lead forms components when no file imports them (a used forms layer keeps the legal components), and their dependencies; a non-literal `import(` makes it refuse and ask for a decision), then `npm install` so the root `package-lock.json` follows, then `npm run lint`. A lint failure is fixed in the code, like a QA failure, never by turning a rule off. If pruning removed files, re-run `npm run qa -- --site <slug>` (step 9) before the final `check-landing`.
2. `npx prettier --write sites/<slug> design-system/<slug>` then `npx prettier --check .`
3. `node scripts/credits.mjs --site <slug> --check`
4. `node scripts/layout-signature.mjs --site <slug> --write` (serves `sites/<slug>/dist`, which the last QA run built, and writes `sites/<slug>/layout-signature.json`), then `node scripts/check-landing.mjs --site <slug> --refs <the url: values from the used sheets' frontmatter>` (always run it; `--refs` only if sheets were used; needs `sites/<slug>/dist/`, which the last QA run built). A `copy-match` failure means a sentence must be rewritten. A `layout-diversity` failure means the composition is too close to another site: change the section patterns, grid, radii, buttons or footer (not only colors and fonts), rebuild, re-measure and re-run. An `archetype-target` warning is not a failure: either bring the page closer to the archetype or list the deliberate deviation in RUN.md "Design decisions". The `scenes` rule fails when a built scene has no poster recorded in `assets.json` or the site has more than two scenes. With AI images in `assets.json` the `ai-provenance` rule fails on an entry without its provenance fields or file, on a brief that does not allow AI images, on a prompt that breaks the prompt policy on a built home page without a visible `data-ai-disclosure` element, on a `subject` other than `owner` and on an owner portrait without both consents.

With a market in the brief: `node scripts/legal.mjs --site <slug> --check`, then `npm run report -- --site <slug> --skip audit` after the last QA run: the `legal-pages`, `legal-cookies` and (with forms) `legal-forms` items must not fail (a `pending` value means the customer still owes data: list it in RUN.md, do not invent it). Without a market the item warns and RUN.md says the legal requirements are unknown.
6. `npm run report -- --site <slug> --only static --skip audit` after the last QA run: no `seo-*` item may fail (a title or description missing, JSON-LD that does not parse, review markup, a `noindex` page in the sitemap, `Disallow: /`), and fix the warns that are in the site's hands (lengths, one `h1`, the keyword in title, `h1` and description, JSON-LD of the brief's type). Write the remaining `seo` warns in RUN.md, for example a missing `site` that the owner sets at hand-off.
7. On a multi-locale landing `node scripts/check-landing.mjs` runs the `i18n` rule and checks the AI disclosure and the business name on every locale home page; read its failures per locale.
8. `npm run check:sites`
9. `npm run qa -- --site <slug>` once more if any file changed after the last QA pass.

With a brief, the check also runs `brief-facts`: a brief fact (business name, primary call-to-action URL, contact email and phone, each product name and price) missing from the built page, or one that sits next to the word "ejemplo", "example" or "sample", fails and names the field. Fix the page, never the brief (the brief is the customer's); if a value cannot be shown, say so in RUN.md and ask the owner. Customer assets must have an `owner` and `permission` in `assets.json` (`images-credited`).

Then fill RUN.md: Images (count, sources, anything dropped, and each AI image with its reason and the count against the cap), Design decisions, Final check results, "to confirm before launch" (placeholders for assumed or empty fields, stock photos, and for a run without a brief sample contact data and prices and hours), "To fetch by the owner" (links behind a login, files the brief names that were not usable), Totals (wall clock from the phase times, approximate tokens if the session reports them). Set `Result: passed` and mark the last rows `done`.

Never commit, push or deploy: the person running this reviews the diff, commits and opens the PR, and CI deploys the preview.
